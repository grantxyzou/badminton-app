# Gotchas — the burns behind the rules

Moved out of `CLAUDE.md` → Gotchas on 2026-10-11. Each entry produced a one-line rule that stays in `CLAUDE.md`; this is what the rule cost, kept because a rule with no story is one people argue with. Some entries describe code that has since moved on (the 2026-05 sign-in flow, for one) — history, not current behaviour.

## Auth — the adaptive Home sign-up form (the members-only OFF path)

- **Sign up** = register for the active session via HomeTab. **With `NEXT_PUBLIC_FLAG_MEMBERS_ONLY` on, everything in this bullet is the flag-OFF path**: the server takes the name from the signed-in account and refuses anyone without one (security rule 13). The sign-up card is an **adaptive form** driven by `useMemberProbe(name)` from `lib/useHasPin.ts` (debounced GET `/api/members/me?name=X`):
  - `anon` mode (probe returned null OR member doesn't exist): name input only → POST `/api/players` `{name}`.
  - `sign-in` mode (member with PIN): name + PIN input + "Forgot your PIN?" link → two-step submit (POST `/recover` to verify PIN, then POST `/api/players` to register for session). Sign-in here AUTO-REGISTERS for the active session because the button label "I'm in this week" makes the intent unambiguous. (Differs from Profile sign-in, which does not auto-register.)
  - `create` mode (member exists, no PIN yet, **and this device holds their `member_session`**): name + Create PIN + Confirm PIN → POST `/api/players` `{name, pin}` (member gets PIN AND session signup in one call). **A no-PIN member on a device WITHOUT their session gets `anon` mode instead** (2026-09-13 flow audit): `create` used to show there too, and the server refuses a first PIN without a session (`account_claim_needs_approval`), so the name-only sign-up regulars rely on failed on every new phone.
  Submit handler in `components/HomeTab.tsx` `handleSignUp` branches by mode.

## Rules and what they cost

- **A rule added to a shared function is worthless if a caller reimplemented it.** `app/api/session/advance/route.ts` kept its OWN inline copy of the three settings-drift comparisons instead of calling `detectSettingsDrift` — and that is the path that stamps `anomaliesAtAdvance`. So a `deadline_changed` check added to `lib/anomalies.ts` would not have reached the code that actually runs at advance time. The 2026-09-03 session closed sign-ups a day early with only `max_players_changed` recorded against it for exactly this reason. Same family as the ten copy-pasted member resolvers `lib/memberResolve.ts` exists to prevent: when told "we already check that", check WHERE.
- **A recorded value nobody compares is not a check.** `PrevSessionSnapshot.deadlineOffsetHours` had been written at every advance and displayed by `SetupPage` since it was introduced, and nothing ever compared it — so a deadline that moved a full day was invisible while `maxPlayers` going 11→12 raised a warning. `detectSettingsDrift` now flags `deadline_changed` past a 6-hour tolerance; the tolerance is not zero because a session crossing a DST boundary moves its wall-clock offset by exactly an hour through nobody's decision, and a warning that fires twice a year for something nobody did is one people learn to dismiss unread.
- **A cache that reads before it checks saves nothing.** `lib/levelStore.ts`'s group-calibration memo scanned the group's whole `gameResults` and all of `assessments` on every call to compute a change signature and only THEN consulted its 30 s cache — the cache saved the fold's CPU and none of the reads that were the cost. Since 2026-09-28 the TTL is checked first, and the two writers (`POST /api/games`, `POST /api/assessments`) call `invalidateGroupCalibration` so a new game shows on the next load. The same day `lib/sharedRead.ts` gained `sharedFetch` (one request per path while IN FLIGHT, each caller its own `Response` clone, no freshness tail because these callers refetch after a write) for the Home and admin-landing duplicates, and `/api/players/unpaid` went player-first (`lib/owedRows.ts`) instead of reading every session and every player row on every Home mount.
- **Catalog seeding REFRESHES, it does not only fill.** `ensureCatalogSeeded` originally upserted only ids that were ABSENT — right for a catalog that grows, wrong for one whose rows change SHAPE. When the v2 import added normalized attributes to 39 rows that already existed in Cosmos, the JSON file gained them and the database never did: `isScorable` then silently skipped **50 of 71 rackets in production** while every local test passed, because in dev the JSON file IS the catalog. It now refreshes a row when it is missing OR its seed-owned fields differ, guarded two ways — only rows marked `seeded: true` are touched (a deploy must never revert an admin-authored row), and the comparison **sorts keys** (Cosmos doesn't guarantee key order, and a plain `JSON.stringify` would call every row stale and rewrite the whole catalog on every cold start). Any future data whose shape changes needs the same treatment.
- **Backticks inside a double-quoted `git commit -m` are command substitution.** `` `seeded: true` `` was executed by the shell and replaced with empty output, silently deleting the phrase it was explaining. Same family as the heredoc `!` hazard. Use `git commit -F -` with a **quoted** heredoc (`<<'MSG'`) — the quotes stop all expansion.
- **A per-task review scoped to its own diff cannot see cross-file breakage.** Twice in one branch a change invalidated assertions living in files the task never touched (a catalog count, then lint errors), and both got through a clean task review. Run the FULL `npm test` **and** `npm run lint` between tasks, not only at the end — the repo baseline is 0 lint errors, so a regression there is unambiguous.
- **Auth cross-call assumption** (lesson from commit `fa7544a`, 2026-05-14): when a client stitches two server calls into one user-visible action, the server has no way to know they're related. The v1.4 unified Home sign-in flow called `/api/players/recover` then `/api/players` and assumed the first verified the user for the second — but /recover doesn't grant any auth cookie, so the second was anonymous and 401'd. **Rule**: every server-mutating call must carry its own credential (admin cookie OR explicit body.pin verified against `member.pinHash`). Don't trust "the previous call just succeeded." Regression test at `__tests__/players-signup-with-pin.test.ts`. (The recover route has minted a `member_session` on a PIN sign-in since WS#3; the rule outlived the specific failure.)
- **Re-check the predicate in JS before a destructive mock-store query acts on a row.** A first cut of `purgeMember` used `@v` throughout, so every query matched the whole container and the purge deleted both kudos rows instead of the one received — type-clean, and it would have passed a less specific test.
- The admin cookie TTL was 8h before v1.3; it was bumped to 30 days to match `badminton_identity`'s localStorage longevity.

## Automation hooks — the burn behind each

- `check-flag-sync.mjs`: `NEXT_PUBLIC_FLAG_SETTLE` was silently off in production for two weeks before the check existed (that flag has since retired; the lesson has not).
- `check-i18n-keys.mjs`: `CLAUDE.md` and the script both claimed next-intl throws on a missing key. It renders the key path (`profile.settings.privacyPolicy` on screen where a label should be), and three message blocks landed under the wrong parent on 2026-08-27 and stayed green all three times; `__tests__/i18n/canary-strings.test.tsx` checks a hand-maintained list of ~12 keys and is structurally incapable of catching a new one. The check runs in 50 ms.
- `block-tab-screenshot.mjs`: documenting the trap did not stop it recurring — hence a hook that refuses the command.
- `block-secret-commit.mjs`: the `.env.local.bak` leak was the one recorded burn without a hook; `*.bak` in `.gitignore` fixed one spelling of it. No entropy scan, because a gate that flares on `package-lock.json` gets muted.
- `check-plan-reviews.mjs`: `docs/plans/value-hub-slice-0.md` carried an honest kill criterion and went unread for ~9 weeks, by which time three of the four tracks it gated had shipped anyway. A criterion with no scheduled read is a note, not a gate; a plan with NO review line is fine — most are finished records.
- `.claude/hooks/session-start.sh` used to announce "soaking on bpm-next" and the `bpm confirm` list — both retired in Aug 2026 — and kept announcing them for weeks. Per-project settings use gitignored `.claude/<name>.local.md` files; templates in `docs/automation/`.
