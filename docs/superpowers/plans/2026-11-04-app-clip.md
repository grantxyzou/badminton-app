# App Clip Build Plan

Intent: docs/plans/native-ios-targets.md

> **For agentic workers:** work task by task, in order. Steps use checkbox (`- [ ]`) syntax for tracking. Phase 0 is Grant's and gates everything after it; Phases 1–2 run in a Linux session; Phase 3 onward needs a Mac build loop.

**Goal:** A person without the app taps an invite link, scans a QR on the organiser's phone, or taps an NFC sticker, and signs up for this week in an App Clip. Then they are offered the full app, which opens already signed in.

**Architecture:** The clip is a small native SwiftUI target beside the Capacitor shell. It calls only existing routes plus one new kind of join request. It holds the member's `member_session` cookie in its own keychain, and the full app moves that cookie into the WebView's cookie store on first launch. The server and web pieces ship first and are useful on every phone before the clip exists.

**Tech stack:** Next.js 16 route handlers and React client components (Phases 1–2); Swift 6, SwiftUI, AuthenticationServices, StoreKit `SKOverlay`, a shared Swift package (Phase 3+); Vitest with the mock store; `__tests__/native-shell-projects.test.ts` for the hand-edited Xcode files.

## Global constraints

- **One person, once.** Every way in keeps `docs/plans/one-time-invites.md`. A permanent URL (the sticker) admits nobody without an organiser's approval.
- **No new container.** The account is at Cosmos's 25-container cap (CLAUDE.md, "New containers"). A new doc kind goes in an existing container with the right partition key and scope.
- **Recipients come from the club's roster**, never a person-level role (`rosterMembers`, as in `app/api/members/access-request/route.ts` since #771).
- **Schema is additive and optional only.** A rollback runs older code against the same database.
- **The clip stays at 15 MB or under.** QR codes and NFC are physical invocations, so the larger digital-only limits do not apply.
- **The clip stores nothing the server cannot give back.** iOS removes an unused clip and its data after about a month.
- **Push payloads carry a name and a club, never money** (the lock-screen rule).
- **Never test against production.** Use the mock store (`npm run dev:next:mock`) and TestFlight.

## Phase 1 — Web pieces, useful before the clip exists

### Task 1.1: "Show as QR" on the Invite card

A fresh one-time invite drawn as a QR on the organiser's screen, scanned by the other person's camera, then the next one. Today it opens the web sign-up on any phone; once the clip ships, the same QR raises the clip card on an iPhone.

**Files:**
- Modify: the Command Center's Invite card (consumer of `lib/useInvites.ts`)
- Create: `components/admin/CommandCenter/InviteQrSheet.tsx`
- Test: `__tests__/components/InviteQrSheet.test.tsx`

- [ ] Choose a QR encoder. It must be small, maintained, MIT or similar, with no network calls, and it must render SVG so it can be themed. Record the choice and the bundle cost in the PR.
- [ ] "Show as QR" mints through the existing invite route and draws its link. It shows the club name and "Scan with your camera" above the code, and the 8-character code below it for a phone without a camera app.
- [ ] When the invite is used, the sheet says so and offers "Next person", which mints the next one. It must not mint on open twice, and must not keep a used code on screen.
- [ ] The QR keeps a light ground in dark mode. A camera reads dark-on-light reliably, and the HIG asks for the code upright and not too small.
- [ ] Tests: the sheet mints once per "Next person", renders the invite's own URL, and shows the used state. Design canaries pass (no raw sizes, colours or radii).

### Task 1.2: The door link (the sticker's server half)

A rotatable club link for a sticker, modelled on `lib/claimLinks.ts`. The difference is that it admits a **new person** after an organiser approves. The claim link only lets an imported, unclaimed name in.

**Decide first (Grant):** reuse the claim link for stickers, or give the sticker its own door link? This plan assumes **its own**. Rotating a leaked chat link must not kill every sticker, and a sticker admitting new people is a wider door than the claim link was approved as.

**Files:**
- Create: `lib/doorLinks.ts` (mint, rotate, resolve; a sibling doc of the `Group` in `groups`, keyed by the hash of the secret, exactly as `lib/claimLinks.ts`)
- Create: `app/api/groups/door-link/route.ts` (organiser: read, mint, rotate)
- Create: `app/api/groups/join-request/route.ts` (unauthenticated: the ask) and its claim route
- Modify: `app/api/groups/preview/route.ts` (accepts the door token, answers the club name only, with the same single 404)
- Modify: `app/api/admin/access-requests/route.ts` and `components/admin/CommandCenter/AccessRequestsCard.tsx` (the request shows "At the door · new")
- Modify: `lib/landingParams.ts` (the new landing param, canary-pinned)
- Test: `__tests__/group-door-link.test.ts`

- [ ] The ask follows `app/api/members/access-request/route.ts` exactly. It is rate-limited before anything, answers one constant 200, hands a secret to the asking device only, and does nothing until a human approves.
- [ ] Where the pending request lives: a new person has no `Member` doc to hang it on. Pick an existing container by partition key and scope (`groups` is GLOBAL and keyed by `/id`), and write the reason in the plan.
- [ ] Approval creates the account and the membership through the same path an invite sign-up takes (`signupGroupFor` in `lib/inviteSignup.ts`), so the roster, the name reservation and the join notice behave identically. Then it signs the asking device in, and Home offers the PIN step (`OFFER_PIN_KEY`).
- [ ] Notify both places (Grant, 2026-11-04): the Command Center inbox, plus a push to the club's organisers (`listOrganisers` in `lib/groups.ts`), tagged per request, opening `?tab=admin`.
- [ ] Rotating the door link cancels its waiting asks, as the claim link's rotation does.
- [ ] Tests: two clubs (a door ask in club X never reaches BPM's inbox or push), the same 200 for every outcome, rotation, approval admits exactly the asking device, and a decline admits nobody.
- [ ] Organiser screen: Roster → "Door link" with Copy, "Write to a sticker" instructions (NFC Tools, **never Lock**), and New link.

### Task 1.3: Count where sign-ups come from

The kill criterion is "fewer than half of iPhone sign-ups arriving by invite link come through the clip". That needs a number.

**Files:** `lib/events.ts`, `lib/authSession.ts`, the sign-up terminals
- [ ] Add `'clip'` to `USAGE_PLATFORMS` (additive). The clip sends a fixed client header on its calls, and the sign-in event records the platform from it.
- [ ] `clubMetrics()` reports sign-ups by platform for the last 30 days, as totals only.
- [ ] Tests: the platform is recorded from the header and defaults to the web value without it.

## Phase 3 — The clip (needs the build loop)

### Task 3.1: `BPMKit`, the shared Swift package

**Files:** create `ios/BPMKit/` (Swift package), consumed by the clip, and later by the widgets, Watch and activities
- [ ] Models mirrored from `lib/types.ts`, covering only what the clip reads: group preview, session summary, sign-up result, invite errors.
- [ ] An API client that holds `member_session` in an `HTTPCookieStorage` the clip owns, sends the fixed client header from Task 1.3, and maps the server's `{ error }` codes.
- [ ] Design tokens from `app/globals.css` (colour, type sizes, spacing, radii), named the same.
- [ ] English strings only (the widget and push rule).
- [ ] Keep it lean, since it counts against the clip's 15 MB.

### Task 3.2: The clip target and its four screens

**Files:** create `ios/App/BPMClip/` (target created once in Xcode, never by hand in the project file, as `native/README.md` says for the widget)
- [ ] Read the invocation URL (`NSUserActivityTypeBrowsingWeb`) and route on `join`, `claim` or the door param.
- [ ] **Club:** the name from `GET /api/groups/preview`, or the one 404 shown as "This invite has been used or has expired. Ask the organiser for a new one."
- [ ] **Sign up:** Sign in with Apple, or a name and a PIN, through the same sign-up terminals the web uses, which settle the invite claim. Then sign up for this week through `POST /api/players`.
- [ ] **Log in and join:** name and PIN through `POST /api/players/recover`, then `POST /api/groups/join` with the invite.
- [ ] **Door:** a name and "Ask to join", waiting on the approval exactly as the web's waiting screen does.
- [ ] **Done:** "You're in for Thursday", then the install card (Task 3.4).
- [ ] Info.plist: the `NSAppClip` dictionary. Leave out `NSAppClipRequestEphemeralUserNotification` until Task 3.5 decides the push.

### Task 3.3: Hand the session to the full app

**Decision:** move the cookie itself, not a migration code. `lib/authMigration.ts` codes live five minutes (`MIGRATION_TTL_MS`), and a person may install the full app hours later. The cookie is the same credential the WebView would hold, lives 30 days, and the full app can read the clip's keychain from iOS 15.4 through the associated App Clip entitlements, which Xcode adds when the app is archived with the clip.

**Files:** the clip (write), `ios/App/App/MainViewController.swift` (read, exists), `__tests__/native-shell-projects.test.ts`
- [ ] The clip writes the `member_session` value and its expiry to its keychain after every successful sign-in.
- [ ] On first launch, before the WebView loads `server.url`, the full app reads that item. If it is unexpired, it sets it into `WKWebsiteDataStore.default().httpCookieStore` with the cookie's own attributes (HttpOnly, Secure, SameSite=Lax, path `/bpm`), then deletes the item. Never on later launches.
- [ ] The full app's cookie wins if it already holds one. A person who signs in to the full app is never signed out by an old clip item.
- [ ] Canary: pin the read and the delete in `MainViewController.swift`.

### Task 3.4: The install card

- [ ] Show `SKOverlay` with an `AppClipConfiguration` once, after the sign-up confirms. Show it again on a later launch only if the person has not installed the app.
- [ ] Never before the sign-up is done, and never as a gate on it.

### Task 3.5: Same-night notifications (only after the transport is settled)

- [ ] Settle the open question in `docs/plans/native-ios-targets.md`: can FCM carry the clip's token, or does it need APNs direct under the clip's bundle id?
- [ ] If yes, add `NSAppClipRequestEphemeralUserNotification`, register the clip's token through `app/api/push/subscribe/route.ts` with an additive platform value, and send only "you're in" and the waitlist promotion (`lib/waitlistPromote.ts`).
- [ ] If no, ship without it. The clip shows its confirmation on screen, and nothing relies on the push.
