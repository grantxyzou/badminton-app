# App Clip Build Plan

Intent: docs/plans/native-ios-targets.md

> **For agentic workers:** work task by task, in order. Steps use checkbox (`- [ ]`) syntax. Part 1 runs in a Linux session; Part 2 onward needs the Mac build loop.

**Goal:** A friend taps your invite link, or scans the QR on your phone. Within seconds they are signed up for this week: in the app if they have it, in the App Clip on an iPhone if they don't, on the website otherwise. If they install the app afterwards, it opens already signed in.

## Priorities, in order (Grant, 2026-11-04: "simplify, reliable, and UX priority")

1. **UX first.** The fewest taps from the link to "You're in". Three clip screens at most. Nobody chooses a link by phone, and nobody signs in twice.
2. **Reliable: never a dead end.** Every step falls back to something that already works today. If the clip card doesn't show, the website opens; if the handoff fails, the app shows its normal sign-in; old `?join=` links keep working. Nothing promises a push it can't send.
3. **Simple: the fewest new parts.** One link format, claimed once. Existing routes only, no new container, no new server concept in v1.

## The one link

**`https://bpm.grantzou.com/bpm/j/<token>`** carries every way in: the one-time invite now, and later the claim link and a sticker's door link. It is the only new path that anything claims:

- The full app on iPhone and Android opens it in place.
- The App Clip experience is registered on it.
- The website answers it by redirecting to the `?join=` page it already has, so the sign-up screens don't change.

It is a path, not a `?join=` query, because App Clip experiences match the start of a URL and most Android versions can only match a path. Claiming the home page instead would pull the Google and Apple sign-in pages into the app and break them. With a path of its own, those pages stay out by construction.

**The weekly sign-up link has its own path too, `/bpm/s`** (Grant, 2026-11-04, after "sign up is acting weird"). It is the noticeboard, not a key: no token, any number of taps. The app claims it exactly (never as a prefix, which would take `/bpm/sw.js`) and opens Home on this week's session, already signed in. The website sends it to Home. Same module, `lib/inviteLink.ts`, and the same three places are kept in step: the AASA, the Android filter and `NativeBridge`.

## v1 scope

**In:** the one link, the full app opening it, the QR on the organiser's phone, a three-screen clip, a signed-in handoff to the full app, Apple's install card, and a count of sign-ups by platform.

**Later, each after v1 is used:**
- **The NFC sticker,** behind your approval (`docs/plans/native-ios-targets.md`). It is a door link on the same `/bpm/j/` path, so it needs nothing new claimed. The stickers stay blank and unlocked until then.
- **"Log in and join"** for an existing account on a phone without the app. That person is rare, and the clip can offer them the install card instead.
- **The same-night notification.** Its server transport to a clip is unsettled. v1 confirms on screen.
- **The claim link on the new path.** It keeps `?claim=` until then.

### Task 1.3: Show as QR

The organiser's phone is the "being close" way in. It is a fresh one-time invite drawn big on screen.

**Files:** `components/admin/CommandCenter/InviteCard.tsx`, a new `components/admin/CommandCenter/InviteQrSheet.tsx`, `__tests__/components/InviteQrSheet.test.tsx`
- [x] "Show as QR" draws the invite the card is showing (its `/bpm/j/` link) as a QR on a light ground, even in dark mode, because a camera reads dark-on-light best. Show the club name above it, and the 8-character code below it for a friend whose camera won't scan.
- [x] When that invite is used, the sheet says "That invite has been used. They're in." and shows **Next person**, which mints the next one. It never shows a used code. (The name would need a new read; the join push already names them.) The sheet polls the club's live list every 3 s while open and on screen, with its own read, so a failed check never tips the card into its error state.
- [x] The QR encoder must be small, maintained, MIT or similar, SVG, with no network calls. Chose `uqr` 0.1.3 (MIT, no dependencies, pinned), which returns the grid; `lib/qr.ts` draws it as one SVG path in the app's own colours.
- [x] Tests: one mint per Next person, the drawn URL is the invite's, the used state appears, and the design canaries pass. Checked in a browser at phone size in both themes: a standard QR decoder (jsQR) read the on-screen code back as exactly the card's link.

## Part 2 — The clip (Mac build loop)

### Task 2.1: `ios/BPMKit`, kept small

- [ ] Only what the clip needs: the club preview, the sign-up result and the error codes; a client that holds `member_session` and sends the client header; and the design tokens it draws with. English strings.
- [ ] It counts against the clip's 15 MB.

### Task 2.2: Three screens

**Files:** a new `ios/App/BPMClip/`, with the target created once in Xcode, never by hand (`native/README.md`)
- [ ] **Club.** "Join BPM Core" with this week's day, from `GET /api/groups/preview`. A used or expired invite shows: "This invite has been used. Ask the organiser for a new one."
- [ ] **You.** **Sign in with Apple** as the big button, one Face ID glance. "Use a name instead" for a name and an optional PIN, through the same sign-up route the web uses.
- [ ] **You're in.** "You're in for Thursday", then Apple's install card. The clip signs them up for this week as part of the same step, so there is no extra tap.
  - A full session says what the server answered: "You're on the waitlist, number 3. We'll move you up if a spot opens."
  - Sign-ups not open yet says: "You're in BPM Core. Sign-ups for Thursday open soon, so get the app to hear when."
  - The screen only ever states what the server confirmed.
- [ ] Every network error gets one plain line and a **Try again** button, and the website link as a way out. Never a spinner without an end.

### Task 2.3: Arrive signed in

Move the cookie itself, not a migration code. A migration code lives five minutes (`MIGRATION_TTL_MS`), and people install hours later.
- [ ] The clip saves `member_session` and its expiry in its own keychain. From iOS 15.4 the full app can read it through the associated App Clip entitlements, which Xcode adds at archive.
- [ ] On first launch, before the WebView loads, the full app (`ios/App/App/MainViewController.swift`) moves an unexpired cookie into the WebView's cookie store with its own attributes, then deletes it. A cookie the app already holds always wins.
- [ ] If anything fails, the app opens to its normal sign-in. The canary pins the read and the delete.

### Task 2.4: The install card

- [ ] Show `SKOverlay` once, after "You're in". Show it again on a later launch only if the app still isn't installed. Never before the sign-up, and never as a gate on it.

### Task 2.5: Guardrails

- [ ] Fail the archive over 15 MB, using the App Thinning size report.
- [ ] `__tests__/native-shell-projects.test.ts` pins the clip's `NSAppClip` keys, its domain entry and its parent app.
