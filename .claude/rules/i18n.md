# Translations (next-intl)

<!-- Moved word for word from the root CLAUDE.md "Gotchas" on 2026-11-09, to keep the always-loaded file short. -->

- **The admin surfaces are English-only, by decision** (2026-09-28 audit, item Q10). `components/admin/**` renders hard-coded English (BirdsPage, SetupPage, the Command Center cards) while every member surface goes through `next-intl`. Three admins, all of whom read English, and ~600 strings to key and translate for nobody: not a gap to close, and not a pattern to copy — a NEW member-facing string always goes through `t()`. **Grant, 2026-11-06: "Admin eventually gets to Chinese"** — so this is the current state, not the destination; when that work starts, this bullet is the place to start, and `check-i18n-keys.mjs` will hold the keys.
- **i18n is cookie-based, not URL-based**: `NEXT_LOCALE` cookie drives the locale. `proxy.ts` (formerly `middleware.ts`, renamed in Next 16) sets it on first visit from `Accept-Language`; `LanguageToggle` writes it on tap. Cookie `path` must be `/bpm` (matches `basePath`) — not `/`.
- **Server reads cookie, client writes cookie**: never use `navigator.language` or `localStorage` for locale — it will desync server and client and cause hydration mismatches. Always go through `useLocale()` on client and `getLocale()` on server.
- **The translations are NOT in the page** (2026-10-19, #650). `app/layout.tsx` passes no `messages`: `components/intl/IntlProvider.tsx` imports them — English bundled, Chinese a dynamic `import()` that `use()` waits for, so an English page never downloads the Chinese file. Handing the merged tree to the provider from the layout put ~37 KB gzipped into every no-store HTML; two providers picked in the layout made every page load BOTH languages. The pure `deepMerge` / `brandMessages` live in `lib/messageTree.ts` so the browser can run them, and `__tests__/i18n/client-messages.test.ts` pins the client trees equal to the server's.
- **Missing translation keys fall back to English**: `i18n/request.ts` deep-merges `messages/en.json` under the active locale, so a missing `zh-CN` key renders the English string rather than throwing. Do not rely on throwing behavior for "missing translation" detection — use the `canary-strings.test.tsx` assertion pattern.
- **next-intl HMR is sticky on new top-level branches**: editing existing keys in `messages/*.json` hot-reloads cleanly, but adding a brand-new top-level namespace (e.g. `admin.resetAccess`, `signup.pinPrompt`) sometimes leaves the running dev server with the old in-memory message tree, so `useTranslations('that.new.path')` throws `MISSING_MESSAGE` even though the key exists in the file. **Restart the dev server after adding any new namespace branch.** `pkill -f next-server` alone races with the next `npm run dev` (the new instance sees port 3000 still bound and exits). The reliable pattern: `ps aux | grep next-server` to find the PID, then `kill -9 <pid>`, then `npm run dev`. Editing nested keys inside an already-loaded namespace doesn't have this problem.
- **What a screen reader says is translated too** (audit, 2026-11-05): a spoken name with no visible text (`aria-label` on the tab bar, the theme toggle, pull-to-refresh, a loading frame's `role="status"`) comes from the `a11y` message group, never a hard-coded English literal; the loading canary exempts `a11y.*` because those strings are never drawn. **A refused action shows OUR sentence, never the server's words**: `POST /api/players` answers in English sentences and snake_case codes alike, and the sign-up card printed whichever came back, so `lib/signupError.ts` maps each one to `home.signup.errors.*` and anything unknown to the generic failure (`__tests__/signup-error.test.ts`); a sheet that builds a key from a code (`` t(`error.${code}`) ``) checks the code is one it has a sentence for, or next-intl prints the key path. A date in a member's sentence takes the APP's locale (`useLocale()`) and `America/Vancouver`, never the phone's (`formatReadyBy(date, locale)`).
- **Rich-text strings use `t.rich`, not `t`**: any message containing `<tag>...</tag>` must be rendered via `t.rich('key', { tag: (chunks) => <Component>{chunks}</Component> })`. Using plain `t()` on a rich-text key prints the raw `<tag>` characters.
- **Component tests need a provider wrapper**: components that call `useTranslations()` must be rendered inside `<NextIntlClientProvider locale="en" messages={enMessages}>` in tests, or they throw "No intl context found". See `__tests__/components/LanguageToggle.test.tsx` for the pattern.
- **One word per idea in what a member reads** (`docs/plans/one-way-in.md`, step 2, 2026-11-13; Grant: "sign up and invite and join all these flows are just over complicated"). **"Sign up" means one thing: putting yourself on a session's list** (Home's card, the push, the help guide). Making an account is **"Join a club"** (Welcome, the invite page), never "Sign up". The thing a person belongs to is a **club** in every member-facing string, English and Chinese (俱乐部, never 群组); the CODE keeps `group` (`Group`, `groupId`, `/api/groups`), and "group chat" (the WhatsApp kind) stays. Chinese already separated the first pair: 注册 is an account, 报名 is a session. The legal pages still say "group" and are Grant's call, not a copy pass.
