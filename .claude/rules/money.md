# Money: the payments inbox and the ledger

<!-- Moved word for word from the root CLAUDE.md "Payments inbox / The ledger" section on 2026-11-08 (it was over the 150k-character limit). The root keeps the always-follow rules; this file loads when Claude touches a matching path. -->

### Payments inbox (e-transfer auto-detection)
`docs/plans/payments.md`, flag `NEXT_PUBLIC_FLAG_PAYMENTS_AUTO` (server-read). The admin's Gmail runs `public/payments/apps-script.gs`, which forwards each Interac notification to `POST /api/payments/etransfer` with `x-payments-key` — a per-club secret (`<groupId>.<hex>`) minted in the admin card and stored as a sha256 in the club's `clubSettings` doc (`paymentsSettingsId(g)`). `lib/paymentsInbox.ts` owns ingest, the key, assign and the soft hold; `lib/etransferParse.ts` and `lib/etransferMatch.ts` are pure.
- **Never guess with money.** Auto-match needs an AUTHENTICATED email (the topmost, `mx.google.com`-stamped `Authentication-Results` shows `dkim=pass` for an `interac.ca` domain AND the From is `interac.ca`) ADDRESSED TO THE CLUB (its To names the script's own Gmail or the club's pay-to address, `addressedElsewhere`; DKIM proves Interac wrote an email, not whose money it was, so a member could re-deliver the notice of a transfer to someone else. A script copy older than 2026-11-05 sends no To and is trusted as before — paste the new one), exactly one candidate person, and an amount equal to one owed line, the oldest k lines, or the whole balance. Anything else is a `review` row in the admin's "Needs a look" list. An unauthenticated email still carries its proposed match, so the admin's tap is a confirmation — after checking the bank. **And only a SETTLED line is ever paid without a person looking** (`settledLines` in `lib/owedBalance.ts`, 2026-10-21): an unsettled past session's live share is what Home shows, but it moves until settle, and a row paid at the estimate was then stamped a different `owedAmount` with `paid: true` already on it, so the difference was never collected and never shown. "Pay with credit" reads the same list; an admin assigning a queued payment by ref may still pick any line.
- **Candidates are what Home shows** — `lib/owedBalance.ts` `computeOwed` is shared with `GET /api/players/unpaid`, sessions AND finished stringing jobs, so a player who sends their Home total matches.
- **Three clues name the person**: the sender's LEGAL name through `aliases` (etransferName → appName), the sender name as a roster name, and the MEMO's tail when it is exactly a roster name (the receipt template `{group} {date} - {name}` puts it there — verified on a real notification). Clues naming two different people are a review, never a guess. The queue's "Remember X as Y" writes the alias.
- **Dedupe is Interac's `Reference Number`** when an authenticated email carries one, else the Message-ID.
- **A Stripe outcome the card webhook cannot act on is a `review` row in the SAME queue** (`fileCardReview` in `lib/cardPay.ts`, 2026-11-16, `docs/plans/money-audit.md` "How BPM stays true with Stripe"): a Checkout whose amount does not match its lines, one from an account that is not the club's, unapplied card money the app could not refund, and a Dashboard refund that names no single line each file a `payments` doc with `source: 'card'`, `card: { checkoutId, chargeId?, kind }` and a `card_*` reason, keyed on the Checkout Session (and the charge, for a refund) so a redelivery 409s; a write that fails THROWS so the webhook answers 500 and Stripe retries — until then these were `console.error` lines nobody read. The inbox card shows them under "Needs a look" as `Card · <payer>` even when e-transfers are not set up. Resolving one goes through `resolvePayment` like any row, with three differences: an assigned card row pays its lines BY CARD under the CHECKOUT id (`applyAllocations(..., via)`), the id the webhook would have written, so a later redelivery finds the rows already its own; `remember` never writes a bank-name alias for card money; and a `kind: 'refund'` row is money OUT and answers `not_a_payment` to an assign — it can only be dismissed. `__tests__/group-card-review.test.ts`. **A redelivery never re-pays or refunds a line its payment ever paid** (2026-11-18): a manual Resend of a three-day-old `checkout.session.completed` in Workbench refunded $13.73 in production, because the lines had changed since and Stripe's 24-hour idempotency key on the refund had long expired; the test then found the same Resend re-paying a line an organiser had un-ticked. `applyPaidSource` now skips any line this Checkout or intent paid once (the row's `paymentId` / `cardPaymentId` / `refundedPaymentId` / `disputedPaymentId`, else `everPaidBy` reading the ledger's payment entry, which stays when voided; unreadable counts as yes) unless the line still holds it now; only money that never found its line is refunded. `__tests__/group-card-pay.test.ts`. **A dispute (chargeback) is the same shape** (`applyDispute`, 2026-11-17): `charge.dispute.created` un-pays the lines the disputed amount names by the refund rule (stamped `disputedPaymentId`) and ALWAYS files a `kind: 'dispute'` row (`card_dispute` / `card_dispute_no_line`), dismiss-only, because the deadline is in Stripe; `charge.dispute.closed` with `won` marks the lines paid by card again under the same Checkout and closes the row, and `mirrorPaid` numbers the re-pay `payment:<row>:<cs>:<n>` beside the voided original (a live member of that family means nothing to write). `__tests__/group-card-pay.test.ts`.
- **A card fee is a surcharge, and the server alone computes it** (`docs/plans/card-surcharge.md`, 2026-11-17). An organiser's switch on the club's `cardPay` doc (`surcharge: { on, bps, acknowledgedAt }`); on, members pay through `CardPaySheet` and `app/api/payments/card/form` instead of Checkout. Credit cards only, at most 240 basis points and Stripe's own `maximum_amount`, rounded DOWN (`lib/surchargeMath.ts`), written onto the PaymentIntent by the server and confirmed as quoted — never an amount from the browser. The webhook applies only intents tagged `bpm_flow: 'surcharge'` and files a review row unless `lines + fee` equals the charge with the fee within 2.4%. A refund returns the prorated fee. The fee is NOT in the ledger (it offsets Stripe's fee, which the ledger does not record either).
- **`Player.paid` stays the truth.** A match writes `paid: true` plus additive `paidAt` / `paidVia: 'etransfer'` / `paymentId`; the admin's manual tap writes `paidVia: 'manual'` — **under the etag since 2026-11-16** (`docs/plans/money-audit.md` gap 3): `PATCH /api/players` writes with `replace`, and a lost race re-reads the row — already holding everything the request asked for (the other tap did it) → 200 with that row and no mirror; holding something else → 409 `changed_elsewhere` and the card reloads. It was an `upsert`, so two taps both wrote and both mirrored (−$60 against a $30 charge), and either could overwrite an e-transfer or card payment landing in the same moment. The self-report flag takes the same write. `__tests__/players-patch-etag.test.ts`. A row already paid or covered when a payment lands is skipped, never overwritten — **and so is a FROZEN line that no longer owes the allocation's amount** (`applyAllocations`, 2026-11-16, `docs/plans/money-audit.md` gap 8; a job at a price other than the one matched): the card path had refused that all along, the e-transfer path marked the row paid at the new amount for a transfer of the old one. An assign that cannot land every line leaves the payment in the queue as `changed_while_matching` with what did land, as the automatic path does; an unsettled estimate picked by ref is a person deciding and is not checked. **A row records what was RECEIVED, not only that it was** (`Player.paidAmount`, dollars, additive, `docs/plans/paid-amount.md`, 2026-11-16): `paid: true` still means paid in full, and a payment short of the bill — only ever a transfer an organiser assigns by hand to lines it does not cover (`spreadOverLines`: session lines oldest first, each down to a part of itself; a job whole or left for the next payment) — leaves `paid: false` with `paidAmount` set, so the row owes `owedAmount − paidAmount` (`classifyOwed` is the one place that subtracts). The tap, settle, card and credit record the whole bill; an un-tick, a card refund and a returned credit clear it. Gap 8's check is therefore "never MORE than the line owes": a bill raised between match and write lands as a part-payment, a bill lowered under the money stays in the queue. Settle makes `paid` follow the money (a row ticked at the estimate records the frozen bill; a short transfer on an estimate is paid once it covers the bill, else owes the rest), and an over-payment is left for the Ledger check to show. Home says "paid $30 of $45" beside the date, the Payments card "Paid $30 of $45" under the name, Profile's chart counts what came. `__tests__/paid-amount.test.ts`. **`paid: true` on a resplit-covered row is an uncover** (gap 7) and takes the same `paid_would_change` check on a settled bill someone has paid; it used to slip past and read "paid $0".
- **The email body is never stored**; `payments` docs are anonymized by `purgeMember`.
- **The soft hold is OFF by default** (`holdAfterUnpaid` 0 in the club's payments settings doc); the admin card shows who it would hold before it is switched on. On, a member owing for ≥ N SETTLED sessions — counted by SESSION, so a plus-one's line on the same night is not a second one, and not counting lines they self-reported — signs up onto the waitlist with `heldForUnpaid: true`; a payment (inbox or manual) releases it, and promotes them only into a spot no earlier waitlister is waiting for. Admin-added sign-ups bypass it, and it fails OPEN on a read error.
- **Reminders** (`lib/paymentReminders.ts`, OFF by default): the club's Gmail script calls `POST /api/payments/remind` daily with the same key — App Service runs nothing on a schedule, and the script already holds the key. A push at settle +3 and +7 days, then silence; settled lines only, never self-reported, never older than 30 days; one push per person; lines stamped in `Player.remindedAt` BEFORE the send, so a crashed run can miss a nudge but never double one. **The run, the card's "would remind" preview and its "would hold" list all come from ONE `computeOwedForRoster` read** (`dueRemindersFrom` / `wouldHoldFrom` are pure over it, 2026-10-21): each used to walk the roster through the per-person `computeOwed` — about four serial round trips a member, twice, on every Command Center open and every payment tap — and `__tests__/payment-reminders.test.ts` pins that `GET /api/admin/payments` never calls the per-person path. **No amount in the body** (lock-screen rule).
- **What a member has PAID is read from the rows** (`GET /api/members/me/payments`, `lib/memberPayments.ts`, Profile → Account balance's chart, 2026-11-09): their own paid `players` rows (`owedAmount`, in the month of `paidAt`, else `settledAt`, else the session's date), their guests' shares (`guestOf`) and their paid `stringingJobs`, through the same player-first reads as the balance (`loadOwedInputs`). Not the ledger, until a reconcile has run clean. A paid row with no frozen `owedAmount` (paid at an estimate, never settled) adds nothing rather than a guess. Always the caller's own, in the club their cookie names (`__tests__/group-member-payments.test.ts`).
- **The pay-to address reaches a member in one place**: `payTo` on `GET /api/players/unpaid` (`lib/payTo.ts`), only when they owe — security rule 10 keeps it off every general read.

### The ledger (store credit, gift cards, and the Phase 2 mirror)
`docs/plans/payments.md`. Container `ledger` (PK `/memberId`, GROUP scoped) is **append-only** — never upsert, edit or delete; a reversal is `void:<idBeingReversed>` (exact negation, keyed on the id it reverses so a double void 409s). **Sums are by `account`, never by partition or kind-list**: a member's partition holds both `member_owed` (charges +, payments/covers −) and `member_credit`; `club_outlay` lives under the `~club` sentinel (court cost per settled session from the snapshot, shuttle purchases, expenses). `sumAccount` / `balanceOf` in `lib/storeCredit.ts`; entries without `account` are credit. **A LISTED credit history is `creditLedgerFor`, never `ledgerFor`** — the balance was narrowed to credit on day one, but the two histories (`GET /api/credit`, `GET /api/admin/credit`) read the whole partition and would have shown charges and voids as "recent credit" the moment the mirror flag went on (review of #562). **A payment entry is what was received** (`paymentEntry(row, receivedCents?)`, 2026-11-16): a live hook passes the delta it just applied, settle and the backfill read the row (`paidAmount ?? owedAmount`, so every row from before is unchanged), a part-paid row gets its entry at settle like a paid one, and an un-tick voids EVERY live payment on the row, so a bill paid in two transfers un-ticks clean. **Ids are derived, never minted** (`charge:<row>:<ms(settledAt)>`, `payment:<row>:<paymentId|ms(paidAt)|legacy>`, `cover:<row>:<ms>:<n>`, stringing `charge:<job>:<n>` and `payment:<job>:<ms(paidAt)>`, `court:<session>:<ms>`, `shuttles:<purchase>`) so a live write, the backfill and a repair compute the same id and the second 409s. **A stringing payment is keyed on `paidAt` whatever the `via`** — until 2026-11-16 a `StringingJob` had no `paidVia`/`paymentId` (a `Player` does), so the backfill could not tell how a job was paid and labelled every one `manual`; **both are additive on the job now** (`docs/plans/money-audit.md`, transparency item 1): the inbox, card, credit and bench paths stamp them with `paidAt`, every un-pay clears them, `mirrorStringingChanged` and `jobEntries` read `job.paidVia ?? 'manual'`, the Ledger check and the job page say the method, and the id is STILL keyed on `paidAt` so no existing entry moved (`__tests__/stringing-paid-via.test.ts`). Before that, the first cut keyed an e-transfer on its `paymentId` and a job paid through the inbox between deploy and backfill would have been mirrored twice (review of #562). **A PAID job cannot be re-priced** (`PATCH /api/stringing/jobs/[id]` answers 409 `job_paid` to a differing `priceCents`, with `force` or as a proposal, 2026-10-21; and since 2026-11-05 so does the player's `accept` of a proposal made before the payment — that route also mirrors an accepted re-price now, which it never did): the payment entry's id is derived from `paidAt` at the price paid, so re-pricing underneath it would leave the job's owed account netting to new − old while the row says paid, and the reconcile would report it daily with no repair (the backfill computes the same ids); the path is unpaid → re-price → paid (a new `paidAt`, so a new payment id at the new amount), and `paid: false` in the same body is accepted because the mirror reads prev against next and sees both transitions. **A hard-deleted PAID session row keeps its charge and its payment** (`mirrorRowDeleted`, 2026-11-16, `docs/plans/money-audit.md` gap 5): only an unpaid row's charge and cover are voided on `purgeOne` / `purgeAll` — the same rule `mirrorStringingDeleted` took in #951, for the same reason: the money was collected, so the bill it paid exists, and voiding the charge alone left a payment nobody was asked for. **A hook that writes a DELTA must first check the base exists**: between deploy (flag on) and the backfill, a row the mirror never saw can be edited, and `mirrorShuttleAdjusted` once wrote `+$20` for a purchase whose `shuttles:<id>` entry did not exist yet — the backfill then wrote the base from the CURRENT cost and the club was out $140 on a $120 purchase (review of #562); with no base it writes the base from `next` and no delta. **`lib/ledgerMirror.ts` never throws** — every hook is called AFTER the primary write, on a TRANSITION only, swallows and counts failures (`getMirrorFailures`), and is a no-op with `NEXT_PUBLIC_FLAG_LEDGER_MIRROR` off; the rows (`Player.paid`, `owedAmount`, `StringingJob.paidAt`) stay the truth until a reconcile has run clean. `lib/ledgerBackfill.ts` writes history with the same builders (`POST /api/admin/ledger-backfill`, the `migrate-groups` key gate, bounded, resumable by `remaining`). **The reconcile (`lib/ledgerReconcile.ts`, stage 2) compares FROZEN money only**: the settled rows and billable stringing jobs Home shows a person (`computeOwedForRoster` in `lib/owedBalance.ts` — the whole-roster read `lib/owedRows.ts` moved the per-person path AWAY from, fine once a day) against the ledger's open `member_owed` balance per `ref.id`; an unsettled session's live estimate is left out because the ledger holds nothing to compare it with. A line nobody on the roster is shown (an unlinked legacy row, a purged member's `~anon` charge, a REMOVED member still owing) takes the ROW as its live side and is counted as `unlisted`, not flagged — the review of #570 caught the removed-member case, which would have turned the card amber daily over a line with no repair. Four codes (`missing_charge`, `missing_payment`, `stale_charge`, `amount_mismatch`), **no auto-repair** (the repair is the backfill again, or the admin redoing the action — a reconcile that wrote entries would be a second mirror with its own bugs). It runs on the daily `POST /api/payments/remind` call BEFORE the `remindersOn` check and never fails that run; the outcome lives on the club's payments settings doc as ids and cents (never names); `GET`/`POST /api/admin/ledger/reconcile` names the rows for the admin and DESCRIBES each (`lib/ledgerReconcileDetail.ts`, read-only, 2026-11-16; Grant: "make the ledger check more descriptive"): the job or session behind it (a job's number, racket, stage, paid, invoiced, archived, or deleted; a row's night, paid, covered, removed) and the ledger's own entries for it, voids marked — and `ReconcileSheet` says what is wrong in a sentence and gives the fix for THAT kind of line (a stringing line never gets the session advice). **The one repair a person can tap** is `POST /api/admin/ledger/repair` (`lib/ledgerRepair.ts`, 2026-11-16): a DELETED stringing job whose live entries are payments and no charge (the old delete voided a paid job's charge) gets the charge back as `charge:<job>:<n>`, dated with its payment, refused for a job that still exists (any change to it heals it) and for nothing to restore; the sheet offers it as "Restore the $X charge" on that line only and re-runs the check. The E-transfers card warns on a mismatch or a check older than 2.5 days. **The money view is `GET /api/admin/ledger` (stage 3)** — `lib/ledgerView.ts` `summarizeLedger` buckets the club's ledger in JS (the mock ignores a date parameter it does not know): income, collected by method (an e-transfer is `etransferAuto` only when its `payments` doc says `matchedBy: 'auto'`), covered, outlay by category, net, and credit liability (positive balances only, never windowed). **A void is dated by the entry it reverses**, or a March charge unsettled in May would net inside May and leave March standing. **Two sources, never one number**: `outstanding` is LIVE from `computeOwedForRoster` (frozen lines, everyone, not range-bound) and `unfinalized` is the live `costSplit` estimate for unsettled sessions under its OWN key, last on the page so it can never read as a total. **And the ledger's cards say when they are in doubt** (2026-11-16, `docs/plans/money-audit.md` transparency item 3): while the last Ledger check has mismatches, is older than 2.5 days or never ran, In and out and Collected by carry an amber `N lines off` / `Unchecked` badge and one sentence naming Still owed as the live figure to trust; Still owed itself carries no mark (it used to wear `ledger ≠ app`, the one card that was right). "Card" reads "Card · before Stripe's fee": the ledger records what was owed, Stripe pays out the net, and the fee is not recorded. **Every entry behind the sums is listable** (`GET /api/admin/ledger/entries?range=`, `lib/ledgerEntries.ts`, `LedgerEntriesSheet`, 2026-11-16, `docs/plans/ledger-entries.md`; Grant: "where did it restore to?"): the club's entries in the page's window, newest first, dated by `effectiveDate` like the sums, each with who, what (a session's night, a job's number and racket, "(job deleted)"), how it was paid, and `reversed`; a reversal and what it reversed both stay, struck through. Read-only. **All or nothing**: any read that throws is a 503 `read_failed` (`read-failed-503.test.ts`) — six true buckets and one silent zero is the lying empty state with a straight face. Admin-entered expenses are `POST`/`GET`/`DELETE /api/admin/expenses` (`expense:<random>` under `~club`, dated by `meta.date`; delete is a void). Sentinel ids (`~club`, `~unlinked`, `~anon`) can't collide with `randomBytes` member ids; `purgeMember` refuses them and **re-keys a purged member's `member_owed` entries under `~anon`** (the club's totals need them) while deleting their credit. The mock ignores partition keys: a `gift:<hash>` ledger entry alone would let two members redeem one card, which is why a gift card is claimed by a `clubSettings` doc first.

**Store credit** (`lib/storeCredit.ts`, flag `NEXT_PUBLIC_FLAG_STORE_CREDIT`): **Members and organisers never read "gift card"** (Grant, 2026-11-12: "I dont think it should be framed as 'Gift card'"): the thing is a **credit code** (充值码), the member's page is **Credit** (余额), the organiser's is **Give credit** and the console card **Credit codes**; Home's link is "Have a code?". The CODE keeps its names (`giftcards` routes, `gift:<hash>` ids, `GiftCardsPage`), and a redemption's stored note keeps its `Gift card · <note>` prefix because `creditLine` reads it — the views draw it in today's words. **A gift card's record is a READING of the redeemer's credit, never a second balance** (`docs/plans/gift-card-ledger.md`, 2026-10-09): `attributeCredit` in `lib/creditAttribution.ts` draws every spend from the oldest source still holding something, a refund gives its spend back to the sources it came from, and `giftCardRecords` resolves an old card's redeemer from its `gift:<hash>` entry while a new one carries `redeemedBy`. **Both organiser doors show the SAME record** (2026-11-12): `giftCardViews` in `lib/giftCardView.ts` is the one shape `GET /api/admin/giftcards` and `GET /api/giftcards` (filtered to the caller's own codes) return, so Profile's Give credit list cannot fall behind the console again — Grant opened it and found none of who, when, where or what's left. **Giving a card is an ORGANISER's** (Grant, 2026-11-10: "gift card should be organizer feature only"): `/api/admin/giftcards` (the console's mint and every card's record) and `/api/giftcards` (Profile's "Give a gift card") both answer `organiser_only` to anyone else, the rank re-read on every call; with groups off every admin is one. The `canGift` switch that handed minting to a helper is retired: nothing reads it and `PATCH /api/members` no longer writes it (`__tests__/group-giftcards.test.ts`). Redeeming is every member's. **Idempotence is in the ids — and Cosmos ids are unique only WITHIN a partition.** A gift card is claimed by a `clubSettings` doc `<giftDocId>:claim` (PK `/id`, so unique outright); a `gift:<hash>` ledger entry alone would let two DIFFERENT members both redeem one card, since the ledger is partitioned by member — and the mock, ignoring partitions, would pass that test. A spend is `spend:<lineRef>` in the spender's own partition (a double tap 409s), and re-reads the balance after inserting, refunding itself if a concurrent spend took it below zero. Gift codes are stored as `clubSettings` docs keyed by the code's hash (`giftDocId`) — the plaintext exists only in the mint response — and unknown/used/malformed all answer one `gift_not_found`. Credit pays a line only when it covers it IN FULL and only a SETTLED one (`payWithCredit`, `settledLines`, oldest first, `paidVia: 'credit'`); if the row moved under it, a `credit_refund` entry returns the money. **A stale spend — written and never finished — is reconciled against the ROW on the next tap or balance read, whatever happened to the row** (`refundStaleSpends`, 2026-10-21): a COMPLETED payment (the common case, forever) is answered by the mirror's `payment` entry with `meta.via: 'credit'` and NO row read; otherwise the row is read: still unpaid → finished; paid another way, covered, removed or gone → `refund:<ref>:<n>`. It walks the LEDGER, not the owed lines, because a row paid by e-transfer is no longer owed and the old owed-line walk never visited it. **An organiser's un-tick of a credit payment goes through a review** (`docs/plans/money-audit.md` gap 6, 2026-11-16; Grant: "un-tick should go through a review"): `PATCH { paid: false }` on a row or job with `paidVia: 'credit'` answers 409 `paid_with_credit`; with `review: true` it files a `source: 'credit'` row under Needs a look (`fileCreditReview`, `lib/creditReview.ts`, keyed on the line and its `paidAt`) and changes nothing. The organiser resolves it there: `return_credit` (`returnCredit`) un-ticks the line, voids its payment and writes `refund:<ref>:<n>` for exactly the net credit still taken for it — both halves idempotent, so a retry completes a half-finished run — or dismiss keeps it paid; `assign` is refused. Until then the row stands, so `refundStaleSpends` cannot quietly re-pay it (`__tests__/group-credit-untick.test.ts`). Before this, the un-tick voided the payment and the member's next balance read re-paid the row with the same credit, which the ledger could not record. Account deletion deletes the member's ledger (credit is forfeited).

## Gotchas

- **`costPerPerson` INCLUDES the organiser fee** (`docs/plans/organiser-fee.md`, 2026-11-12). A club's `ClubRun.organiserFee` (dollars, default 0, not part of any style) is copied onto a session at advance as `Session.organiserFee`, and `costSplit` adds it to every share of a PRICED session — never an unpriced night, never re-spread by a resplit cover, forgiven with the share by an absorb cover. Settle freezes it as `SettledSnapshot.organiserFee`; the receipt shows it as its own line between "Split N ways" and "Per person". So `costPerPerson × playerCount ≠ totalCost` once a fee is set: never work a denominator back out of the two (`buildReceiptInput`'s fallback does, but only for legacy snapshots with no `playerCount`, which also predate the fee). The same fee for every player, however they pay: it is the club's price, NOT a card surcharge, which Canada caps at 2.4% on credit cards only.

- **Previous session snapshot**: `session.prevSessionDate` and `session.prevCostPerPerson` are frozen at advance time. `<PrevPaymentReminder />` renders below the sign-up card, gated on `hasIdentity` (not `isSignedUp`) — so players who played last week still see what they owe even before signing up for the next session (research finding 4.8). `hasIdentity` must be kept in sync with `setIdentity` / `clearIdentity` call sites. - **Cover modes (`Player.coverMode`)**: a covered (`writtenOff:true`) player is `'absorb'` (admin eats their share; they stay in the per-person denominator) or `'resplit'` (excluded from the denominator → spread across the other payers). Legacy `writtenOff` with no `coverMode` reads as `'absorb'`. Settle (`/api/session/settle`) is the single calculator and stamps `SettledSnapshot.coveredTotal` (Σ per-person over absorb-covered). `CoverSheet` re-freezes the bill when the session was already settled so amounts update immediately — through `lib/resettleSession.ts`, the ONE owner, shared with `PaymentsCard`'s uncover. **Since 2026-11-05 that is ONE request, `POST /api/session/settle { resettle: true }`, and it keeps EVERYONE the frozen bill billed** (`__tests__/settle-resettle-keeps-billed.test.ts`): it was DELETE then POST from the browser, the POST billed only rows still on the list, and so "Cover & remove" (the club absorbs) and "Remove without covering" (they still owe) both put the removed person's share on everyone else and wiped their debt. A row removed after its bill froze is still a participant, still owes (credit may pay it), and still "attended" in a member's history. A change that would move what someone ALREADY PAID is refused before any write — the re-settle answers 409 `paid_would_change` with the names, and `PATCH /api/players` refuses a resplit cover (or uncover) on a settled bill anyone has paid — because a paid row re-stamped at a new amount keeps `paid: true` over a figure nobody paid. A manual unsettle (DELETE, "Edit the bill") forgets the bill — **and is allowed with people paid since 2026-11-18** (Grant: the extra is "income for me"; it was refused as 409 `bill_has_payments` from 2026-11-16, money audit gap 2, because the re-settle could only stamp a new amount over `paid: true`). The unsettle voids the charges, covers and any kept over-payment but leaves every PAYMENT standing, and writes `paidAmount` on a paid row that predates the field, so each row carries what it received; the Ledger check reads an unsettled row whose payments equal its `paidAmount` as right, not a gap. The re-settle then lets the money decide: received ≥ the new bill → paid, and anything above it is an `overpaid:<row>:<ms(settledAt)>` entry (`overpaidEntry`, `kind: 'overpaid'`, positive in `member_owed`, so the row nets to zero) that the money view counts as `income.overpaid`; received < the bill → `paid: false`, owing the rest. An un-tick voids the kept entry with the payment and REMEMBERS what the row received above its bill (`Player.unpaidReceived`); the next tap on the Payments card asks whether that money really came in, and `PATCH { paid: true, restoreReceived: true }` (admin) records it again and brings the kept share back (`mirrorKept`, numbering the re-keep beside the voided original), while a plain re-tick records just the bill. The Payments card says "Paid $30 · $10 kept". The re-settle with `resettle: true` (a cover change) still refuses `paid_would_change`. `__tests__/money-audit-gaps.test.ts` GAP 2. Surfaced in `PaymentsCard`'s per-player menu (unconditional since `NEXT_PUBLIC_FLAG_LEDGER` retired 2026-08-29).
- **The Payments card shows one session at a time** (`docs/plans/payments-today-first.md`, 2026-10-21): ‹ › step to the neighbouring sessions and the date opens `SessionDatePicker`, a month calendar where only session days are buttons and each carries its money as a dot (amber owing, grey all paid, green the current session); ‹ carries an amber dot while an earlier month still owes. It replaced a grid of every session as a chip. The dots read `GET /api/sessions/history?counts=1` — counts only, no receipts, up to 200 sessions — because the receipt list stops at 24 and an older debt then had no mark at all. A session the counts never answered for gets no dot, never "all paid". The rules are `lib/sessionCalendar.ts`, and so is the cap: `SESSION_CALENDAR_LIMIT` bounds both that `counts=1` read and `GET /api/sessions` (the picker's list, projected to the nine fields the card and `AssignUsageSheet` read — never a `SELECT *` over the history again), so the list and its dots stop at the same session.
- **`lib/buildReceiptInput.ts` is the single cost-per-person + receipt resolver**: computes `costPerPerson` once and returns a ready `ReceiptInput` — snapshot-first for settled sessions (the cover-aware `SettledSnapshot`), best-effort recompute via `sessionCostTotals` otherwise. Drives `GET /api/sessions/history`, `PastSessionsPage`, and `PaymentsCard`'s summary header + receipts, so a list amount and its receipt can't diverge. Don't hand-roll a fourth cost computation (settle, `members/[id]/history`, and this each grew their own). **The denominator itself is `costSplit` in `lib/sessionCost.ts`**: settle freezes what it returns, `buildReceiptInput` and the history route call it for an unsettled session and take `session.settled` for a settled one, and `CommandCenter` calls `buildReceiptInput`. **The LIVE estimates go through it too since 2026-10-21**: `classifyOwed`'s ctx carries the session's ROWS (`roster`, from `loadOwedInputs`' one projected read of the unsettled sessions — two more fields, no extra query) and the advance route's `prevCostPerPerson` fallback calls `costSplit` over every row of the current session, so Home's balance line, the advance snapshot and the receipt cannot disagree over a cover resplit before settle; a count cannot carry a `resplit`, which is why the ctx is rows and not a number (`__tests__/live-estimate-one-rule.test.ts`). `PaymentsCard`/`PastSessionsPage` own their OWN `<ReceiptSheet>` because `CommandCenter.openReceipt` fetches the ACTIVE session only and can't render a past session's receipt.
