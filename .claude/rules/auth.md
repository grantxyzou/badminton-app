# Sign-in, identity and the admin cookie

<!-- Moved word for word from the root CLAUDE.md "Gotchas" on 2026-11-09, to keep the always-loaded file short. -->

- **Auth taxonomy** (since 2026-04-30, restructured 2026-05-12): three distinct concepts, but the user-facing surfaces are unified.
  - **Sign up** = register for the active session from Home's card; the server takes the name from the signed-in account (rule 13). The adaptive name-and-PIN form that was the flag-OFF path was deleted when the flag retired (2026-10-17); its history is in `docs/gotchas-history.md`.
  - **Create account** = identity-only creation, still lives in Profile's `CreateAccountSheet` for invite flow (`sessionSignup: false`). Refuses with 409 `account_exists` if a member already has a `pinHash` (prevents account hijack).
  - **Sign in** (Profile path) = name + PIN auth via `<SignInForm>` rendered inline on ProfileTab's anonymous view (and on the members-only Log in page, with `probeName={false}` — telling a stranger whether a name has a PIN is the oracle members-only closes). POST `/api/players/recover` verifies against `members.pinHash` and returns **identity-only** (`deleteToken: null`). **Its `sessionId` is optional**: absent, the active session is resolved server-side, because the signed-out screen cannot read the session and handing it the id would publish the date — Profile sign-in does NOT auto-register for a session. Constant-time miss against `FAKE_HASH`. Rate-limited 5/hr per `(name, IP)`.
  - **Cancel spot** ≠ **Sign out**. `HomeTab.handleCancel` (moved from the retired Sign-Ups tab) removes the user from the active session player list and zeroes the deleteToken (server consumed it), but preserves name + sessionId in localStorage. The user stays signed in and can re-sign-up with one tap. `clearIdentity()` belongs only in `ProfileTab.handleLogout`.
  - PINs scrypt-hashed via `lib/recoveryHash.ts`. Lost-device admin code via `POST /api/players/reset-access` (10/hr per IP, 6-digit, 15-min TTL, dead after `MAX_CODE_ATTEMPTS` (5) wrong tries; on someone who holds a rank it is an organiser's call, `organiser_only`, because the code clears the PIN). Stored as a scrypt hash on the MEMBER DOC (`Member.recoveryCode`) by `lib/memberRecoveryCode.ts` — it survives cold starts. This line used to name an in-memory `lib/recoveryCodes.ts` that "does NOT survive cold starts"; that file was deleted when the code moved onto the member doc, and the stale warning had people designing around a constraint that no longer exists.
  - **Recovery code path clears `members.pinHash`** (and the `players.pinHash` mirror) on success — the user reached this path because they forgot their PIN, so any subsequent `RecoveryPinSheet` should render in 2-field mode (no current-PIN prompt). Without this, the sheet's `hasPin` check left users stuck after a reset. **It also mints a `member_session` cookie** (consuming a valid admin-issued code proves identity, same as a PIN sign-in) — this is what lets the user pass the members/me first-set guard below when they pick a replacement PIN. (WS#3, 2026-06-03.)
  - **`PATCH /api/members/me` first-PIN set (claim flow) requires identity proof** (WS#3, 2026-06-03): a `member_session` cookie for that name (minted at sign-up, PIN sign-in, or recovery-code reset) OR admin. Previously name-only — member names are enumerable via `GET /api/members`, so anyone could claim an unclaimed (no-PIN) account and sign in as them. The **change-PIN** branch is unaffected (`currentPin` is its credential). Client-side: `GET /api/members/me` returns `authed`; `ProfileTab` passes it to `RecoveryPinSheet`, which blocks first-set with actionable guidance (`profile.pinNeedsSignIn`) when known-not-authed (e.g. cookie expired past its 30-day TTL while `localStorage` identity persists), and never blocks on `authed === null` (unknown — server is the backstop).
  - Profile signed-in: **one row, `How you sign in`**, opens the `WaysToSignInPage` (`components/profile/WaysToSignInPage.tsx`, 2026-11-09, spec §9): the methods card (`SignInMethodsCard`, embedded), then `Update PIN` and `Have a recovery code?`. It used to be three rows on Profile, the first opening `SignInMethodsSheet` (deleted). The row carries a summary (`PIN · Google`) and goes `accent` when the server sets `nudge: true`. Its data comes from `useSignInMethods()`, owned by `ProfileTab` and handed to the page so the row and the page cannot disagree; it is gated on `identity` because the anonymous card must not probe `/api/auth/methods`.
  - PIN management lives on that page as `Update PIN` → `RecoveryPinSheet` (Set/Change only — no Remove), shown only while the member HAS a PIN (`pinIsSet === true`; unknown shows the neutral `pinSectionTitle`). Nobody is offered a NEW PIN there: PINs are being phased out (2026-11-07). A recovery-code redemption still opens `RecoveryPinSheet` in first-set mode. Status sourced from `/api/members/me?name=X` returning `hasPin`, refetched on identity change.
  - **PIN is opt-in** — nothing forces one.
  - **Log in leads with the email code** (step 6, 2026-11-14): Apple and Google, then "Email me a code"; name and PIN sit behind "Other ways to log in" (`LogInView`, `mode` starts at `'email'`). PINs keep working for everyone who has one.
  - **Email code** (`docs/plans/one-way-in.md`, step 3, 2026-11-13): Log in's email form leads with "Email me a code"; the password is a tap away ("Use my password instead", which carries "Forgot your password?"). `POST /api/auth/email-code/start` answers every address with the same `{ ok: true }` and does NOT await the mail (a second's send only for real addresses would put the answer in the response time); `POST /api/auth/email-code/verify` answers every refusal with one 401 `invalid_code` at one scrypt (`lib/emailCode.ts`, constant cost), clears the code with `IfMatch` on the doc it checked (single use; a racing second phone gets a 412 and the same 401), marks the address verified if it is the account's own, and signs in through `completeSignIn(..., 'email_code')` asked for `resolveGroupId(req)`, as the password route is. The code is `Member.emailCode` (scrypt hash, 10 minutes, 5 wrong tries counted under an etag, a new one replaces it) and is a STRIP-CANARY in `publicMember`. Limits: start 10/hr per caller and 3 per 15 minutes per address; verify 20/hr per caller and 10/hr per (address, caller). It signs in an EXISTING account only; making one with a code is step 4.
  - **The club's link signs in FIRST, then asks** (`docs/plans/one-way-in.md`, step 4a, 2026-11-13). Signed out, the link (`/bpm/j/<token>` with a door preview, or `?claim=`) opens `DoorJoinPage`: Apple, Google, or an email code, then "Your name on the list", then the ask. The ACCOUNT is made before anyone approves, in no club: `signupGroupFor` reads a token that is not an invite as the club's link and answers `{ groupId: null, door }` (the email-and-password route refuses it: no password for a new person), and `complete-signup` files an account-bound ask (`StoredJoinRequest.askedBy`, no secret, 14 days, one per account per club, pointer on `Member.joinAsks`). A NEW address gets its code from `email-code/start` only with a live link (stored in `authhandoff` under the address's hash); `verify` then parks the address in the pending-signup cookie as `provider: 'email'`, so the one name step (`complete-signup`) makes every new account. The no-club page shows the account's own asks (`decidePage` → `asks`, `WaitingAsks`, polling `GET /api/groups/ask` every 20 s while visible and switching in once let in). A signed-in member asks from `JoinGroupPage` (`POST /api/groups/ask`). Approval (`POST /api/admin/access-requests` with `regular`) adds THAT account as a regular or a drop-in, and `tellJoinerTheyAreIn` sends an email and a push. `GET /api/auth/methods` reports `hasEmailCode` (an email identity), which counts as a way back in for Home's "Keep your account", the nudge and Profile. **An imported name is linked at approval** (step 4b): `GET /api/admin/access-requests` gives a join `linkTo` when the club's holder of the asked-for name has never signed in (`linkableHolder`: unclaimed, active, not the asker), and the card offers "Yes, that's {name}" (`decision: 'link'`, `linkJoinRequest` in `lib/joinRequests.ts`). The link moves the ASKER's identities onto the HOLDER (`reassignIdentity`), merges its providers and email, and retires the asker (`active: false`, `mergedInto`, `mergedInGroup`); it refuses an asker already in a club. `GET /api/groups/ask` answers the retired account's cookie with `relinked` and a session as the holder, and `approveAccountAsk` refuses a retired asker. **The link takes no name from a signed-out phone** (step 4d): "Claim your name" and the ask form's club-link mode (email field, one-word hint) are gone; `access-request` with a `claimToken` stores nothing, and its poll reads by the seal like any ask. **The signed-out ask says nothing about which names exist** (step 4c): `POST /api/members/access-request` seals every secret it hands out with its hour (`sealAskSecret`, `lib/askSecret.ts`), stored or not, and `access-request/claim` opens the seal first (`openAskSecret`): inside its hour every miss is `pending`, past it `none`. Only a stored, approved ask is `approved`. Never answer a miss from the store: that was the oracle. **The club's link is the only way in** (step 5): one-time invites, their codes and `/api/groups/join` are gone; Join a club asks for the link (`SignUpView`, `JoinGroupPage`), `?join=` lands on the club's page like `?claim=`, `signupGroupFor` answers `{ door }` or `{ door: null }` (creating a club) and refuses everything else, and the email-and-password route makes an account only inside Create a club. **"Is that you?" at the ask** (step 6): through a club's link, `complete-signup` answers 409 `name_taken` before making anything when the asked-for name belongs to an ACTIVE member of that club who has signed in before (`!isUnclaimed`); the name step (`DoorJoinPage`'s claim stage, or `ChooseNameSheet` after Google/Apple) asks for their PIN or an organiser's code and `claim-name` joins the new sign-in to them in the club the link names (an email-code sign-in by its address). A never-signed-in holder still gets an ask (4b). **Never-approved accounts are deleted after 14 days** (step 6): every new account carries `Member.noClubSince`, and the hourly tick's `strayAccounts` job (`lib/strayAccounts.ts`) deletes one still on no roster and asking nowhere, through `purgeMember`.
  - **Admin login**: per-player auth via name + own PIN (`POST /api/admin`); cookie HMAC-signed via `SESSION_SECRET`. `member.role === 'admin'` required. Bootstrap names via `ADMIN_NAMES` env var. **Cookie TTL is 30 days** (`COOKIE_MAX_AGE_S` in `lib/auth.ts`).
  - **AdminTab has no standalone Sign-out button** (since v1.3) — single auth surface lives in Profile. Profile logout calls `DELETE /api/admin` to clear the admin cookie.
- **`IDENTITY_EVENT`** (`lib/identity.ts`): a `CustomEvent('badminton:identity-changed')` is dispatched from `setIdentity` and `clearIdentity`. Page-level state (admin nav refresh in `app/page.tsx`) and `ProfileTab` subscribe so sign-in/out reactivity works without refresh. Browser `storage` events fire only in OTHER tabs — the custom event is needed for same-tab updates. Any new component mirroring `getIdentity()` in local state should subscribe.
- **Admin-only settings live behind `/api/admin/settings`, not `/api/members`**: scanning the public members list for `role: admin` is fragile (multiple admins, response-shape changes leak attributes). The auth-gated `GET/PATCH /api/admin/settings` reads/writes the calling admin's own `eTransferRecipient` and `skipDates`. Used by `SkipDatesEditor`, `ETransferRecipientEditor`, `AdvanceSessionForm`, and the `CommandCenter` receipt loader.
- **The shell's `showAdmin` is the ROLE; the admin COOKIE is a separate fact** (2026-11-06, Grant: "the add a job stringing job save button does not work"). `HomeShell` shows admin surfaces when `GET /api/admin` says the admin cookie is live OR `members/me` says the role is admin, so an admin whose `admin_session` lapsed while the member cookie lived on still sees them — and every admin route checks the cookie. The Stringing bench opened, its job list said "Try again", `GET /api/members` answered the non-admin roster (no ids), so the player search found nobody and "Save job" never turned on. A screen whose reads need the admin cookie gates on `adminCookieLive` (passed down as `knownAuthed` / `adminSession`, `null` while unknown) and shows `AdminSignInCard` (`components/admin/AdminSignInCard.tsx`, the one PIN sign-in, shared with the Admin tab) in front of the work; a sign-in on either calls the shell's `refreshAdminAccess` so the other opens too (`__tests__/components/StringingTab.test.tsx`).

## Members only: the page gate

<!-- Moved word for word from the root CLAUDE.md on 2026-11-09 (step 2 of the trim), to keep the always-loaded file short. -->

**Members only (`docs/plans/members-only.md`; its flag `NEXT_PUBLIC_FLAG_MEMBERS_ONLY` retired 2026-10-17, ON branch kept): the page decides who is signed in ON THE SERVER, before it reads anything.** It calls the same `requireMember` the API routes use, on a `NextRequest` built from its own cookie header — not a second definition of "signed in". Refused → it returns `<SignedOutShell>` (`components/onboarding/SignedOutShell.tsx`: Welcome with Join a club / Log in, then a page for each) and reads nothing; passed → `HomeShell` gets `memberName`, the verified name. **With groups on there is a THIRD outcome** (`decidePage` in `lib/pageGate.ts`, 2026-10-07): a signed-in ACTIVE member with no membership in the claimed group — a new organiser half-way through "Create a club", or someone removed from the club their cookie names — gets the same shell in `noClub` mode (Create a club / I have an invite / Sign out, or a list of their other clubs to pick from) and still reads nothing; `HomeShell` never mounts for them. That is the members-only half of Phase 5's "what does a person in no club see", confirmed by Grant on 2026-10-09 (he kept the list over an automatic switch to the oldest group). The members-only-OFF half closed when the flag retired on 2026-10-17: there is no OFF case any more. A client-side gate over HomeShell would not do: child effects run before a parent's, so the tabs would fetch the roster before the gate decided. **Signing in anywhere on that screen reloads** — every way in ends in `setIdentity`, the shell answers IDENTITY_EVENT with one guarded `location.reload()`, and the server renders the app; there is no client-held opinion of "signed in" to drift from the cookie. `HomeShell` reconciles `badminton_identity` to `memberName` (a shared phone can hold the previous person), and Home's sign-up card is locked to that name — no name field, no PIN field, no `members/me` probe. The iOS-PWA handoff collection lives in `lib/useHandoffCollect.ts`, shared by both shells.
