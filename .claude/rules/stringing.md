# Stringing service

<!-- Moved word for word from the root CLAUDE.md "Gotchas" on 2026-11-09, to keep the always-loaded file short. -->

- **String stock is COUNTED from jobs, never logged** (`docs/plans/string-inventory.md`, 2026-10-10): `lib/stringStock.ts` `summarizeStringStock` takes purchases — `kind: 'stringPurchase'` rows in `clubSettings`, beside the gift cards, NOT a container of their own — and counts one set per job in `STRUNG_STATUSES`, matched to the offered list by label; a purchase mirrors to the ledger as kind `expense`, category `strings`, id `strings:<id>`. The offered list's `links` map (label → catalog id, additive on `OfferedStringsDoc`) is what gives a string its member-facing page (`StringsWeOfferCard`) and its reel length; a PATCH without `links` keeps the stored ones. **The first cut ensured a `stringStock` container on first touch and production answered the Bench "Couldn't load the string stock" the day it shipped** (2026-10-10): creating a container was the one thing that route did that nothing else in production does, and a shared-throughput Cosmos database refuses a 26th (`docs/azure.md` §3 — the code defined 27 and the portal count was never read). The likeliest cause, so the fix stops needing a container; the 503 now carries `step` naming the read that failed, and `ensureContainer` logs `[ensure-container]` on a refused create. **A new container is a known cost, not a free line in the registry** — count first.
- **The stringing notification seam has adapters on both sides now.** `lib/stringingNotify.ts` builds the notice; `lib/stringingNotifyDispatch.ts` sends it from `PATCH /api/stringing/jobs/[id]` when the status ACTUALLY moved. Two channels, and they are INDEPENDENT: **push runs ABOVE the email gate**, because the dispatcher used to return early on `no_email` and `Member.email` is only populated by the email/password and Google paths — wiring push in below that gate would have shipped a channel that reached almost nobody while every test stayed green. Push is the channel that works for a PIN-only member, which is most of them. **The push body carries no money at all** — not the exact figure and not the band. That is stricter than `toPlayerJob` on purpose: a banner renders on a locked phone, in a gym, in front of whoever is standing there, and "your racket is ready" is complete without a price. **A NEW REQUEST pushes too** (`lib/stringingRequestNotify.ts`, 2026-10-11, `docs/plans/stringing-audit-fixes.md`): every admin on the group's roster, minus the requester, gets "Lin's Astrox 88D Pro is waiting on the bench" — player and racket, no spec, no money — and an ASSIGNMENT pushes the assignee ("…is yours", `?tab=stringing`), never a self-claim. Not every `canString` member on the request: when that was decided a non-admin stringer's card showed only jobs assigned to them, so that push led to nothing. **A request NOBODY MOVES nudges the stringers** (`lib/stringingNudge.ts`, 2026-11-12, `docs/plans/stringing-request-nudge.md`): still at `requested` 48 hours after it was made, and again at 3 days, it pushes every `canString` member and organiser of the club (or only its stringer once someone has it), stamped in `requestNudgedAt` under the job's etag BEFORE the send so it never goes twice; the hourly tick (`lib/tick.ts`, `POST /api/cron/tick`, `.github/workflows/tick.yml`, `CRON_KEY`) runs it. A stringer's card lists those requests under "Waiting for a stringer" with Take it (`PATCH { memberId, claim: true }`, their own and nothing else), and any request past 48 hours wears `.bpm-job-card--waiting` on the bench and the card (`lib/stringingWaiting.ts`, one rule for all three). **The player hears about FORWARD moves only** — an undo (`ready` → `strung`) says nothing, where it used to send "being strung" right after "ready". Before that nothing told anyone a request existed; three unclaimed requests showed as "1 need you" on Profile, which now counts unclaimed and overdue jobs as a fourth signal (`benchSignals` in `lib/useAdminNeedsYou.ts`, shared with the Command Center's bench row, which leads the list with "N waiting · M late"). The same audit split `requested` out of `with_stringer` into its own player stage, `awaiting_dropoff` (a racket still in the bag is not "with" anybody; the name is deliberately not `requested`, because `stringing-rules` pins the two unions disjoint), folded the bench's set-up cards under a collapsed "Set-up" below Archived so the list comes first, and took "Grant" out of every player string — `docs/roles.md` strips the stringer on purpose, and a second club reads them too.
- **A player sees their own stringing price EXACTLY** (since 2026-10-28, `docs/plans/stringing-canvas-redesign.md`; Grant: "dont hide"). `toPlayerJob` sends `quote` (the stringer's figure, dollars) and, once the job is billable — finished, priced and unpaid (`lib/stringingBilling.ts`) — `amountDue`, the figure the balance card adds. It was a $4 band (`$28–32`) until then; `priceBand` is gone. Money on the stringing surfaces goes through `fmtMoney` in `lib/fmt.ts` (whole when whole, never rounded). The email quotes the figure; **the push still carries no money**, and a stringer who is not an admin still sees none (`toStringerJob`).
- **String stock is counted per COLOUR once a purchase carries one** (`docs/plans/string-stock-by-colour.md`, 2026-11-11). `StringPurchase.color` is an optional palette id (`lib/stringPalette.ts`) — absent is "Mixed / not sure" and every older purchase — in the same `clubSettings` row; no new container or kind. `summarizeStringStock` keeps two pools per line: one per tagged colour, one mixed. A strung job draws from its colour's pool when that colour was bought tagged (`colourIdOf` maps the job's free-text `stringColor` — the palette's English names, which the catalog shares — to an id), from the mixed pool otherwise; a dry colour never borrows. The line's total, band and cost are unchanged, so the per-colour view can only be more cautious. **Both job reads must project `c.stringColor`** (`app/api/stringing/stock/route.ts`, `lib/stringShelfRead.ts`), or every job counts as mixed. **The request sheet's colours come from `requestColours` in `lib/stringShelf.ts`, never the catalog directly**: the stringer's reel colours (`OfferedStringsDoc.colours`), else the maker's; narrowed, when any purchase is tagged, to `colourStock`'s in-stock ids plus the base list while the mixed pool has sets. Out of stock is HIDDEN (Grant: let the stringer's colour edits decide, "so this scenario will not be run into"). The public `colourStock` map says which colours, never a count. The sheet sends the palette's ENGLISH name as `stringColor` (the bench reads it) and shows the translated one.
- **A stringer who is not an admin may rename a shelf string and set its reel colours** (`docs/plans/stringer-shelf-edits.md`, 2026-11-12; Grant: "open up reel and string name, colour for stringers"). `PATCH /api/stringing/strings` takes, from a live member cookie that `canStringIn` THIS club, exactly one of `{ rename }` or `{ colours: { <label>: ids } }` (merged into the stored map by `mergeColours`; an empty list clears it) — any other key, or both at once, is `403 forbidden_field`, never quietly dropped, the same rule the jobs route keeps for a stringer. The stringer's answer is `{ strings, colours }` only (no prices, links or aliases). The colours-only shape is open to an admin too. UI: `components/stringing/StringerShelfCard.tsx` under the stringer's queue on "Stringing jobs"; its sheet saves the rename FIRST and then the colours under the new name, with one Save in the footer.
- **A job can be for a WALK-UP, someone not on the roster** (`docs/plans/stringing-walk-ups.md`, 2026-11-12; Grant: "give me the ability to add a job for people thats not in the roster"). `POST /api/stringing/jobs { walkUp: true, memberName, walkUpContact? }` (admin only) ignores any body `memberId` and mints `~walkup:<16 hex>` as the job's partition key, one per job. The `~` makes it a ledger sentinel (`isSentinelLedgerId`), so purge and the credit route refuse it, and a MEMBER job with a `~` id is refused. `isWalkUpJob` in `lib/stringing.ts` is the one test. Nothing is PUSHED to a walk-up (`notifyPlayerOf*` return `reason: 'walk_up'` before any read); **one whose contact is an email gets two automatic emails** (Grant, 2026-11-12): the spec from `POST` after the create and a ready email from `PATCH` on the first FORWARD move to `ready`, through `lib/stringingWalkUpEmail.ts` (the member email's transport and sender, never throwing), each stamped AFTER the send in `walkUpEmails.{spec,ready}` (`{ at, ok }`) — a sent one never repeats, and admin-only `PATCH { resendSpecEmail: true }` resends only a failed or missing spec. `walkUpEmailOf` is the one test. Any walk-up's job page shares a receipt image (`StringingReceiptSheet`, drawn in `lib/receiptTemplate.ts`) that names the person, never the contact. A `propose` on their job is applied at once, and a direct re-price needs no `force`, because nobody can confirm it in the app. `job_paid` still holds. `walkUpContact` reaches admins, and the assigned stringer through `toStringerJob(job, { contact: true })`, never the `unclaimed` list, a player or a push. Money uses the existing paths: no member's balance reads that id, the mirror writes its charge and payment under it, and the reconcile counts an unpaid one as `unlisted`.
- **A job counts against the shelf by more than its exact label, and a deleted job keeps its set used** (2026-11-12; Grant: "the stock is not going down based on the archived and finished stringing job"). Two causes, both fixed in `summarizeStringStock` / `lib/stringStock.ts`: (1) the bench fills a job's string from the player's BAG, where a catalog string is named "Yonex BG80", and stock matched only the shelf label "BG80" — so a job's label now tries, in order, the exact label, an alias, the catalog's `brand model` and `model` of a LINKED shelf string, then either with spaces and punctuation gone (`compactKey`), each only where it names exactly ONE shelf string (an ambiguous name stays in `unmatched`, never guessed); (2) deleting an archived job removed its usage — `DELETE /api/stringing/jobs/[id]` now writes a `kind: 'stringUse'` row in `clubSettings` (`su-<jobId>`, label, colour, day, nothing about the person or money) BEFORE removing a job in `STRUNG_STATUSES` (a failed write stops the delete), and both stock reads fold those rows in through `withDeletedUses`, which skips a row whose job still exists. Any new stock reader must read `readStringUses` too, or a deleted job's set comes back.
