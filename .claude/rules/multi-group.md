# Groups (multi-group)

<!-- Moved word for word from the root CLAUDE.md "Groups" section on 2026-11-08 (it was over the 150k-character limit). The root keeps the always-follow rules; this file loads when Claude touches a matching path. -->

Several clubs in the one deployment, chosen 2026-09-07 for the store launch. **ONE ACCOUNT, MANY GROUPS**: `Member` stays the person; a `Membership` carries the per-group role. Flag `NEXT_PUBLIC_FLAG_MULTI_GROUP`, read server-side, **ON in production since 2026-10-22** (#700, `deploy-next.yml`); setting it back to `'false'` is the whole rollback, and off means every request resolves to group `'bpm'` and nothing observable changes. What remains is a SECOND club created and run through one session end to end, then the leak read (`docs/plans/multi-group.md`, Review on 2026-11-25), then `TOLERATE_UNSTAMPED = false`. Phases in `docs/superpowers/plans/2026-09-07-multi-group.md`.

- **`lib/containers.ts` is the one registry** of partition key, scope, reason and provisioning per container; `lib/groupScope.ts`'s three tables, `lib/memberPurge.ts`'s partition keys (`pkFieldOf`) and the provisioning canary all derive from it, and `__tests__/containers-registry.test.ts` pins it to the source scan. The mock ignores the partition-key argument, so a key that comes from the container name rather than the caller is what stops a wrong one passing CI and 404ing in production.
- **`lib/groupScope.ts` classifies every container** as GROUP_SCOPED (filtered by `groupId` on every read, stamped on every write), PERSON_SCOPED (keyed by the person, never filtered by group — but any club AGGREGATE over one must be narrowed to the roster first) or GLOBAL. `__tests__/group-scope-coverage.test.ts` fails the build on a container in none of the three (the tables are views of one `scope` field, so "in two" is impossible by construction), and pins the set to `lib/memberPurge.ts`'s so the two authoritative lists cannot drift.
- **`groupId` is an additive optional FIELD, never a partition key**, and **BPM's ids are never rewritten**: group #1 keeps `session-YYYY-MM-DD`, `active-session-pointer` and the `stringing*` settings ids; only a NEW group gets a `${groupId}:` prefix via `groupDocId()`. That is what keeps rollback safe (older code reads `groupId` as an unknown field).
- **`groupScope(groupId)` is the only way a route reads or writes a GROUP_SCOPED container.** `query` is a builder, not SQL rewriting: pass `{ select?, where?, params?, orderBy?, limit? }` and it emits the group clause itself, wraps your WHERE in parentheses, appends `c.groupId` to a projection so every row can be verified, and excludes from `sessions` reads both the group's own pointer doc (a row in that container, stamped with its group and carrying no `datetime`) and BPM's legacy `'current-session'` doc — pass `includeLegacy: true` only for a whole-history scan that wants it (bird stock, a member's history). **Add `partitionKey: <value>` ONLY when the WHERE is a plain equality on the container's own partition key** (`c.sessionId = @sessionId` on `players`, `c.memberId = @memberId` on `ledger` / `stringingJobs`, `c.recipientMemberId` on `kudos`, as a top-level AND conjunct with no top-level OR) — it runs the query against ONE partition instead of fanning out to every physical partition and merging; it is opt-in, never inferred from the WHERE (a parameter inside an `OR`, `IN` or `ARRAY_CONTAINS` would silently drop rows), the accessor throws on a `/id`-keyed or non-GROUP container, and since the mock ignores the option `__tests__/group-scope-pk-hint.test.ts` source-scans every hint against its WHERE, its params and the registry (2026-10-21). It refuses `DISTINCT`, `TOP` and any `VALUE` other than `VALUE COUNT(...)`, because those are the shapes it cannot verify and the mock (no projections) would never show it. `read`/`replace`/`remove` take the partition-key VALUE only when the registry says the key isn't the id, and `read` checks the key FIELD on the doc that came back — Cosmos 404s a wrong-partition point read, the mock finds by id alone. **A point-read miss of either kind is SILENT** (a foreign id is a legitimate 404: a stale tab after a group switch), while every QUERY row is re-checked in JS and a mismatch is dropped with a `[group-leak]` log — that sentinel means "the clause let a row through". **Every drop is also WRITTEN DOWN since 2026-10-24** (`lib/groupLeaks.ts`, Grant: "track what got leaked"): one `kind: 'groupLeak'` record per distinct (container, asking club, row id) in the GLOBAL `groups` container — never the row's contents — read back as `leaks` on the operator-only `GET /api/admin/migrate-groups`. Strict mode waits on that read, not on someone watching the log stream. **Use `replace` for a read-modify-write**, never `upsert`: `upsert` resurrects a doc deleted between the read and the write (a stringing job archived and deleted from one phone while a status tap lands from another), `replace` verifies first and resolves `undefined` instead. **And `replace` is etag-conditional since 2026-10-21**: it sends `IfMatch` with the `_etag` on the doc you pass — the one your read returned, carried along by the `{ ...row, paid: true }` spread — and a 412 resolves `undefined` exactly like a vanished doc, so `undefined` means "gone OR changed under you; re-read and decide". Two taps that both read `paid !== true` used to both write, and a credit spend racing an e-transfer ingest charged a member twice. A doc with no etag (a seed, a hand-built row) replaces unconditionally. `__tests__/group-scope-coverage.test.ts` fails the build on raw `getContainer('<group-scoped>')` anywhere in `app/` or `lib/` outside a five-file allowlist (`lib/groupScope.ts`, `lib/cosmos.ts`, `lib/memberPurge.ts`, `lib/groups.ts`, `lib/groupBackfill.ts`) — **and on a DYNAMIC `getContainer(expr)` too**, held to the same allowlist. The scanner resolves a string literal and a single-level `const` alias; a container name that arrives as a PARAMETER resolves to neither and used to be dropped in silence, so a file could reach every group container with no canary able to name one. That gap is why `lib/groupBackfill.ts`'s own allowlist entry exempted nothing on the day it was written — `components/`, `scripts/` and `__tests__/` are not scanned, and today hold no such read. During the sweep it was a RATCHET with a `MIGRATION_BACKLOG` keyed per (file, container); Phase 1b (2026-09-09) emptied and deleted it, because an empty backlog left half the assertion unable to fail. Re-add one if a container is ever re-scoped to GROUP. Naming a caller parameter `@groupId`, `@pointerId` or `@legacyId` throws. **Bind `@sessionId`, never `@sid`**: the mock filters by parameter name, and six reads bound `@sid` and returned every row in tests for months.
- **The lib helpers over GROUP containers take the group, so a route cannot call them unscoped**: `resolveBirdUsages(raw, scope)`, `resolveIdentity(arg, groupId)` (members stay a person; only the `aliases` half is per club), `writeEvent(evt, groupId)`, `readShopOpen(groupId)` / `readOfferedStrings(groupId)` / `readPricing(groupId)` with the three `clubSettings` singletons at `shopDocId(g)` / `stringsDocId(g)` / `pricingDocId(g)` (bare `'stringing…'` for BPM, `'<g>:stringing…'` otherwise). Stringing job numbers (`J-0001`) count per group. `__tests__/group-isolation-1b.test.ts` is the two-group gate for `birds`, `aliases`, `kudos`, `stringingJobs`, `clubSettings` and `events`: each case seeds a row stamped `groupId: 'other'` and reads as BPM. **The club AGGREGATES over PERSON containers are narrowed too** (Phase 2 PR 10): `stats/club/bands`, `stats/club/gear` and the level fold's self-seeds in `lib/levelStore.ts` all pass through `rosterMemberIds(groupId)` from `lib/roster.ts`. No `groupId` on the row can separate these — an `assessments` or `playerGear` row belongs to a PERSON, who may be in two clubs — so the ROSTER is the only thing that can. `__tests__/group-isolation-sweep.test.ts` is their gate, and it seeds a whole cohort per side because `tallyClubGear` publishes nothing fewer than `CLUB_GEAR_MIN_COHORT` (3) people share. The narrowing is FLAG-GATED: flag off, `rosterMemberIds` would answer "every ACTIVE member", which is very nearly the same set but drops a soft-deleted member's data, and that correction rode in with the cutover (2026-10-22) rather than ahead of it.
- **A NAME MEANS SOMETHING ONLY INSIDE A GROUP** (Phase 2 PR 3, 2026-09-10). `resolveActiveMemberId(groupId, name)` / `resolveActiveSubject(groupId, name)` in `lib/memberResolve.ts` take the group FIRST so no route can resolve a name unscoped: flag on, the lookup is a POINT READ of the group's name-reservation doc (`${g}:name:${lower}`) followed by an ACTIVE membership check — never a `members` scan, where the same name is a different person in a different club; flag off, it is the `LOWER(c.name)` scan it always was — unless the caller passes the optional `{ memberId, name }` hint from `verifyMemberAuth`, in which case a member asking about THEMSELVES is one point read (taken only for an ACTIVE member whose stored name is the one asked about; anything else falls back to the scan). **And a name-keyed read is gated BY ID** (audit, 2026-11-05, `__tests__/group-same-name.test.ts`): `ownsNameOrAdmin` wraps `nameOwnership`, which with groups on reads the club's reservation for the asked-for name and compares its `memberId` with the cookie's — never the cookie's ACCOUNT name with the asked-for ROSTER name, which refused a renamed member her own balance and let a second Lin read the first's; `matchesIdentity` never matches a row carrying a `memberId` by name, and `resolveIdentity` resolves a name inside the club and keys its names on the roster name. **The roster is `lib/roster.ts`** (`rosterMembers`, `rosterMemberIds`): flag on, the group's memberships joined to their Member docs with the group's roster NAME and ROLE overlaid (`Member.name` is the person's default display name, not what this club calls them); flag off, every active Member. Any club AGGREGATE over a PERSON container narrows to `rosterMemberIds()` first. `GET /api/members` is the roster (a non-admin gets `rosterPublicRows` — name, active, avatar — and only an admin takes the full read); `POST /api/members` and the players route's admin auto-create add a MEMBERSHIP (the invite list IS the roster); both players invite gates and the `members/me` probe resolve through the reservation. **Club settings live on `groups.settings`** — `/api/admin/settings` reads the group doc when the flag is on and it exists, falls back to the calling admin's Member doc otherwise (BPM before the backfill), and PATCH writes BOTH (the Member fields stay for rollback). `SetupPage` reads that endpoint, not `members.find(role === 'admin')`.
- **The strip sites are two helpers now** (`lib/publicShapes.ts`, 2026-09-28): `publicMember` drops `pinHash`, `recoveryCode`, `passwordHash`, `emailVerification`, `passwordReset` and `email`; `publicPlayer` drops `deleteToken` and `pinHash` (sign-up adds the minted token back on that one response). The auth-strip canary checks the helper's destructure and that `members`, `admin/settings` and `players` go through it rather than growing a hand copy. `lib/apiFetch.ts`'s `isRefused(res)` is the client twin: the one reading of 401-or-403. Beside it, `isNoActiveSession(res)` is the one reading of a new group's 404 `no_active_session` — a STATE, not a failure; two admin screens told every new organiser "Couldn't check" / "Couldn't load" until 2026-10-09.
- **Both cookie-jar bridges park the group** (Phase 2 PR 10). `HandoffDoc.groupId` (OAuth, `lib/authHandoff.ts`) and `MigrationDoc.groupId` (the native link, `lib/authMigration.ts`) are stamped at start/mint from `resolveGroupId(req)` and preferred by the claim routes over the request's own. Both flows exist BECAUSE they cross a cookie jar — the system browser sheet, the native shell — so the claim sees no `member_session` and would resolve BPM for everybody, handing a member of another club a cookie claiming a group they are not on the roster of. Additive: absent means BPM. **The dev seeds write what the backfill would** (`seedDevGroupMembership` in `lib/cosmos.ts`): the group doc, a membership per seeded Member, and each name reservation. Stamped rows with no group doc are a HALF-migrated deployment, a state production never sits in, and turning the flag on against it made every roster empty and every admin a 401 — which reads as a broken feature, not as missing seed data.
- **A NAME AND A PIN MAY NOT BE ENOUGH** (Phase 2 PR 9, 2026-09-10). One club made `members[0]` unambiguous; with groups on, two clubs can each have a Lin. `signInCandidates(name, groupId | null)` in `lib/memberResolve.ts` is the single owner of "who could this be?": flag off it is the `members` scan it always was; with a group context (`explicitGroupId(req)` — the cookie claim, or `null`, **never** `resolveGroupId`'s BPM fallback) it is the reservation walk; with none it is `findMembershipsByRosterName`, the second and last cross-group raw read in `lib/groups.ts` (`groups-lib.test.ts` pins the count at 2). Candidates are deduped by MEMBER, so one person on two rosters under the same name is one match, not an ambiguity, and the OLDEST `joinedAt` decides which group their session names. `POST /api/players/recover` verifies EVERY candidate on both the PIN and the recovery-code path before deciding anything and signs in only on **exactly one** match: short-circuiting leaks which account exists, and a distinct "which one did you mean?" would be an oracle saying two accounts share a PIN, so every other outcome returns the same 401. `MAX_SIGNIN_CANDIDATES` (5) is a scrypt-COST ceiling on a B1 tier, not tidiness — past it the attempt fails generically and logs the count rather than deciding among an arbitrary subset. `POST /api/players/reset-access` is admin-authed, so it resolves inside the ADMIN's group; it had the same `members[0]` bug, and the code it issues CLEARS a PIN, so one club's admin could have locked another club's member out.
- **The backfill is `lib/groupBackfill.ts`** behind `GET`/`POST /api/admin/migrate-groups` (Phase 2 PR 4, 2026-09-10). `GET` is the status the Phase 5 flip is gated on: per group container, the count of rows with no `groupId` — counted in JS from a `NOT IS_DEFINED` projection, because the mock applies no WHERE and a `VALUE COUNT` would count every row in tests. `GET` also reports `members.mismatched` (an `active` flag that disagrees with its membership) and `names`: `duplicates` (name groups sharing a reservation key), `blockedRejoins` (**per MEMBER** — removed members whose exact name an ACTIVE member now holds, so they cannot come back under it) and `similar` (ADVISORY: groups a person reads as one name that the reservation treats as two, `Chris L.` vs `chris l` — nothing is blocked). **The first two are keyed by `rosterNameKey`, the reservation's OWN key, and must be.** A first cut folded punctuation away for all three and broke the rule at both ends: punctuation variants reserve DIFFERENT ids, so it called a rejoin blocked that was not, and a CJK name folded to the empty string and was skipped — a roster of non-Latin names reported a serene zero while the backfill refused on the collision. A report about a constraint has to be keyed the way the constraint is keyed. A roster name is unique inside a club BY CONSTRUCTION (the reservation doc's id IS the name, so the second claim 409s on insert), which means a clash cannot be created and so cannot be found by looking — these counts and the `roster_name_taken` 409 from `POST /api/members` are the only two places it is ever visible. `POST { dryRun }` needs the admin cookie AND an `x-migration-key` header equal to `MIGRATION_KEY` (App Settings; hashed both sides then `timingSafeEqual`; unset → 503, never an open door; rate-limited before auth). It creates `groups/bpm` from the owner's own settings (owner = first `ADMIN_NAMES` name, else earliest active admin, else earliest active member), one membership per Member (`active: false` → `removed` with the name NOT reserved; two ACTIVE members sharing a name is a reported COLLISION, never a throw — rename one and re-run). **It RECONCILES, it does not only create**: the whole backfill window ran flag-off (until 2026-10-22), and flag-off `POST`/`DELETE /api/members` moves `Member.active` without touching memberships, so between runs a restored person can hold a `removed` membership (unresolvable the instant the flag goes on, name unreserved) or a departed one can hold a live name reservation. A re-run rejoins or removes them, the owner excepted — an inactive owner is reported, because handing a group on is a person's decision. `GET`'s `members.mismatched` is what makes that visible: a membership ROW is not the gate, and `withoutMembership: 0` reads green over both cases, and stamps `groupId: 'bpm'` on every unstamped row under `IfMatch` — conditioned on the etag the SCAN returned, so a row edited in between is counted under `conflicts` and picked up by the next run rather than silently overwritten. **Every scan is BOUNDED**: `POST { limit }` caps the rows stamped PER CONTAINER (default 2000) and the summary's `remaining` names the containers with more, because `events` has no ceiling and Azure App Service ends a request at 230s — an unbounded run would 504 with no report. The status `GET` caps the same way and lists `truncated`; a zero is always exact, which is all the cutover gate needs. Idempotent: "run until `GET` is all zeros" is the operating procedure, and the limit is what makes that literal. Prod order: deploy flag-off → `GET` → dry run → run → `GET` zeros → flag on → a SECOND club created and run through one session end to end → `GET`'s `leaks` reads zero → `TOLERATE_UNSTAMPED = false`. Done through "flag on" on 2026-10-22 (the re-run read `mismatched: 0` that day, and #700 deployed the flag). **Grant, 2026-10-24: don't ask him to monitor leaks until a second club has done a full session** — with BPM the only club there is nothing for a leak to cross into, so a quiet week proved little. Both `GET` and `POST` are OPERATOR-ONLY since the same day: with groups on, `isAdminAuthedWithMember` admits any club's admin, and this status is deployment-wide. **"The operator" is `isOperator` in `lib/operator.ts` since roles v2 PR 3 (2026-11-03)**: the member ids in the `OPERATOR_MEMBER_IDS` App Setting, each still an active admin somewhere; while that setting is UNSET it is the rule from before, an admin of BPM, so nothing locked the day it deployed — set it, because once BPM has several organisers and admins "an admin of BPM" is a club's power, not a person's. Release notes are the deployment's, so `POST`/`PATCH`/`DELETE /api/releases` are the operator's too (the Command Center row shows only when `GET /api/admin` answers `operator: true`), and `/api/claude`, which any club's admin may use, carries a per-person daily cap besides its per-IP one. The operator's one cross-club write is `POST /api/operator/membership` (`docs/plans/roles-v2.md`): any rank in any club, an organiser's included — the one exception to "nobody removes an organiser" — behind the rate limit, a listed operator's cookie AND `x-migration-key`; every use is a `kind: 'operatorAction'` doc in the GLOBAL `groups` container, awaited before the route answers and read back as `operatorActions` on this `GET` (`__tests__/group-operator.test.ts`).
- **Invites are ONE-TIME since 2026-10-06** (`docs/plans/one-time-invites.md`; Grant: "lets make it one time used link"), and `lib/invites.ts` is the only file that mints, lists, revokes, resolves or claims one. An invite is a link (`?join=<32 hex>`) and an 8-character code that admit ONE person, once, within seven days; the admin makes one per person from the Command Center's Invite card (which also draws it as a QR code for the person standing there, `lib/qr.ts` over `uqr`, and saves it as a poster image), and the weekly "Share sign-up link" carries NO invite (a one-time link in a chat is used up by the first tap). Both docs are SIBLINGS of the `Group` in the GLOBAL `groups` container, keyed by the hash of the secret (`invite:${sha256(token)}`, `code:${sha256(code)}`), so "which club is this for?" is a POINT READ. **The club record is the authority**: `Group.invites` lists the live pairs, an invite is live exactly while listed and unexpired (a comparison on READ), and `claimInvite` removes it under an `IfMatch` etag so two sign-ups racing on one link cannot both get in — the second replace is a 412. **Claim first, release on refusal**: `signupGroupFor` claims, both sign-up terminals settle the claim after the fact (`finalize` on a 201, `release` on anything else), and `POST /api/groups/join` finalizes only a FIRST join — a member already on the roster tapping a link meant for someone else gets "welcome back" and the link survives. `finalize` drops the plaintext from both docs. The legacy club-wide pair (`Group.inviteId` / `inviteCodeId`, a doc with no `pairId`) is never resolved and never written again; the fields stay for rollback. `GET /api/groups/preview` is the ONE unauthenticated route in the group API and returns the club's NAME and nothing else; every failure — unknown, used, expired, revoked, closed — answers one identical 404. **The mock store's `item.replace` honours `IfMatch` and mints an etag since the same day**; before that every read-modify-write under `replace` looked race-safe in tests while the mock could not produce the 412 their retry loops exist for.
- **A club's LINK is how anyone joins it** (`docs/plans/claim-your-name.md` 2026-11-04, `docs/plans/door-link.md` 2026-11-05, `docs/plans/one-way-in.md` step 4, 2026-11-13). One reusable `?claim=<32 hex>` per club, shared as `/bpm/j/<token>` (the preview answers `kind: 'door'`), stored like an invite (`claimlink:${sha256}` beside the `Group`, `Group.claimLinkId` the authority, `lib/claimLinks.ts` the only owner); a new link retires the old one. **It takes no name from a signed-out phone since step 4d**: the person signs in first (Apple, Google or an email code, `DoorJoinPage`) and the ACCOUNT asks (`Group.joinRequests` with `askedBy`, `lib/joinRequests.ts`: 14 days, one per account per club, at most 50 open). Only an ORGANISER approves or declines; approval adds that account as a regular or a drop-in, and an imported name nobody has signed in under is LINKED to the asker at approval (step 4b). A name a member already holds is shown as taken and refused at approval, never handed over. `POST /api/members/access-request` with a `claimToken` stores nothing and answers the same sealed secret as any ask, for a page left open from before; a phone-bound join row (a `hash`, no `askedBy`) is neither listed nor approvable and lapses within its hour. The signed-out "let me in" ask (Log in's "I play here already") remembers its club (`StoredAccessRequest.groupId`; absent = whichever roster holds the person, from the phone's last club), so the push goes to that club's admins (`rosterMembers`, never a deployment-wide `role = 'admin'` scan), the card and the approval are that club's, and the claim's cookie names it. **"Sign out everywhere"** (`Membership.sessionsNotBefore`, also stamped by issuing a recovery code) is refused wherever the member cookie is re-read: `activeMemberFor` (page gate, members-only reads, sign-up, widget) and `verifyLiveMemberAuth` / `readLiveMemberSession` in `lib/auth.ts` — the cookie's identity plus one point read of the membership it names — which every write acting as the member, every path that hands back a session (first PIN, provider link, migration link, create/join/switch a club) and the page gate's no-club fallback use. `verifyMemberAuth` alone is blind to it, and so is every `lib/` helper built on it (`callerMemberId`, `ownsNameOrAdmin`, `nameOwnership`, `peekMemberSession`); `__tests__/member-session-cutoff-coverage.test.ts` lists each function still calling one with the reason it may, fails on a new one, and fails on a blind `lib/` helper that is not in its `WRAPPERS` list, so a wrapper cannot hide its callers (`auth/nudge` wrote on the Member through `callerMemberId` until 2026-11-09; a write from either cookie takes `liveCallerMemberId`). **So is an `admin_session`**: `isAdminAuthedWithMember` compares the cookie's `iat` with the same field on the doc it already re-reads (no extra read), so `requireMember` and `callerMemberId` stop falling back to a signed-out admin; the sync `isAdminAuthed` stays blind, as it is to a demotion, and the same canary fails a write that trusts it alone. Because it ends a console session, signing out an admin or organiser is an organiser's call (`organiser_only`); an admin signs out members and themselves.
- **Two canaries watch the sweep itself** (Phase 5, 2026-10-08). `__tests__/setup/group-leak-spy.ts` is a vitest `setupFiles` entry that fails any test during which `groupScope()` logged `[group-leak]` — the line was the flip's production sentinel and nothing in the suite read it; a test that provokes it on purpose calls `allowGroupLeakLog()`. `__tests__/group-sweep-coverage.test.ts` requires every route calling `groupScope(` or `resolveGroupId(` to be imported by a `__tests__/group-*.test.ts` file; the routes that predate it sit in its `UNSWEPT` ratchet (62 of 84 on the day, 48 after batch 2 on 2026-10-09 — `__tests__/group-isolation-sweep-2.test.ts`, one person on both rosters so only the group can separate them), which fails on a new gap and on a stale entry, so it can only shrink.
- **The sign-ups-open push goes to `rosterMemberIds(groupId)`, not `sendPushToAll`.** `pushSubscriptions` is PERSON-scoped and a person can be in two clubs, so nothing on the row could separate them; the roster is the only thing that can. `__tests__/session-signup-open-push.test.ts` seeds a second club and asserts its member is NOT in the recipient list, and asserts `sendPushToAll` is never called at all — reaching for the unnarrowed sender is the regression.
- **A per-club trust lives on the MEMBERSHIP, not the person** (2026-10-11). It began with `Membership.canGift` (retired 2026-11-10: giving a card is an organiser's, by this club's rank): a Member-level switch cannot say WHICH club granted it, so a helper on two rosters could have minted one club's liability against the other. **The same rule took `role`, `active` and the roster `name` on 2026-10-24** (security review): with groups on, `PATCH`/`DELETE /api/members` write them to the MEMBERSHIP — the only place flag-on auth and the roster read them, so the Roster sheet's "make admin" and "restore" had written a `Member` field nothing read since the flip — and the Member copy only when the admin's club is BPM (flag-off IS BPM, so that is the only rollback copy that means anything); a club-x admin writing `Member.role = 'admin'` onto a person also in BPM would have minted a BPM admin for the day the flag came off. An organiser (`owner`) is never demoted or removed there (`owner_immutable`) — **and since roles v2 (2026-11-03, `docs/plans/roles-v2.md`) a club may have SEVERAL, only an organiser hands out a rank or gives a gift card (`organiser_only`; `isAdminAuthedWithMember` answers `organiser`), and an organiser stops being one only by stepping down (`POST /api/groups/step-down`; the last one passes the club on through `reassignOwnership`).** `stage` and `clearPin` stay person-level by decision. `__tests__/group-admin-scope.test.ts` holds it. **`canString` moved the same way on 2026-11-03 (roles v2 PR 2)**, reversing the 2026-10-24 call to leave it: `Membership.canString` is what the bench, the stringer view and the assign picker read through `canStringIn` / `stringerIn` / `listStringers` in `lib/roster.ts`, an ADMIN grants it (no organiser needed), `PATCH /api/members` writes both copies, and a BPM row never set reads the Member's value so nobody dropped off the bench on deploy (`canStringOf`; `__tests__/group-stringers.test.ts`). `__tests__/group-giftcards.test.ts` holds it.
- **How a club runs is a SETTING, never a special case** (`lib/clubRun.ts`, `docs/plans/six-feathers-onboarding.md`, Grant 2026-10-29: "treat the real demo club as a real group just with different setting configuration"). `GroupSettings.run` holds one value per rule (`playersPerCourt`, `money`, …) and a `style` (`first_come` = BPM, `members_first` = Six Feathers, or `custom`) that fills them in; picking a style writes its values, and a single hand edit makes the club `custom`. **Absent means BPM**, so BPM Core reads exactly as before. Every behaviour reads `clubRunOf(settings)`, never the raw field, and a gap is filled from the club's own STYLE, so a setting added later reaches the clubs that chose that style. The route stores the whole object and works the style out from the values (`parseClubRun`); members see it through `memberVisibleSettings`, admin screens through `useClubRun()` (`known` gates any hiding — unknown is not "off"). **A setting joins the model only when it does something**: a style that wrote a value nothing reads would be a switch that lies. `money: 'off'` hides the Payments card, the Money rows, "N unpaid" and the bill actions, and puts `SessionListCard` under the session card in Payments' place — the week's list with remove, add, move to and from the waitlist, restore, the late-cancel tag and a guest's invite, and NO money field in its row type, so none can leak in (`docs/plans/money-off-session-list.md`; the per-row calls both lists send are `lib/sessionRowActions.ts`); `playersPerCourt` sets the cap from the courts in both session forms.
- **`TOLERATE_UNSTAMPED`** (same file): while `true`, `groupClause()` emits the tolerant WHERE fragment under which a row with no `groupId` reads as BPM's. **The mock store keys its `@groupId` tolerance on the QUERY TEXT, not the constant** (`__tests__/mock-store-groupid.test.ts`): only a query carrying `groupClause(true)`'s `NOT IS_DEFINED(c.groupId)` marker gets legacy rows back, so a plain `c.groupId = @groupId` excludes them in the mock exactly as Cosmos does. The first cut keyed on the constant alone and was laxer than production — the same mock-vs-Cosmos trap as the PK argument. And before the mock knew the name at all, an isolation test would have passed vacuously (unrecognised parameter = no filter).
